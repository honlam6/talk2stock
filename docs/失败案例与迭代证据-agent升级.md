> 用途：课程 Final 报告 failure analysis 素材 + 后续回归防护清单。

## C1 · 复合问题被规则直答截胡，只答一半（2026-10-24）

- **现象**：问「今天卖了多少？另外库存的货总共值多少钱？」，命中规则直答层 `today_stats`，只回答了第一半；第二半（库存货值）静默丢失。
- **根因**：规则直答的护栏只有句长（≤24 字）。该复合句 18 字，含「今天…卖…多少」即命中，没有多意图检测。设计规则层时的盲区：只考虑了"长句复杂"，没考虑"短句也可以复合"。
- **修复**：`ask.py _rule_route()` 加第二道护栏——含「另外/还有/以及/顺便/然后/同时/再问/还想知道」等连接词一律放行给 agent loop。
- **证据**：修复前真机响应 `route: rule, tool: today_stats`（只含今日统计）；修复后同问句 `route: agent`，两工具链式取证。单测 `test_misses_go_to_agent` 增加两条复合连接词用例。
- **防御**：规则层的准入条件每加一条，必须配一个"不得命中"的对抗用例。

## C2 · SSE 事件数据形状不一致 → 工具名渲染成 undefined（2026-10-24）

- **现象**：/ask 流式界面步骤行显示「✓ undefined」，点击展开是空白。
- **根因**：后端 step 事件把记录字段平铺在事件顶层（`{"step":1,"tool":...,"type":"step"}`），其中 `step` 是**步序号**；前端写 `paintStep(ev.step || ev)` 想兼容两种形状，但 `ev.step` 是数字 `1`（真值），`||` 短路后把 `1` 当记录传给渲染函数 → `s.tool` undefined。
- **修复**：后端统一事件信封 `{"type":"step","step":{记录}}`；前端只取 `ev.step`。
- **证据**：视觉模型评审截图发现「✓ undefined ˅ 是 P0 级 bug」；修复后 DOM 快照显示「✓ 今日经营 305ms」。
- **防御**：①事件协议一旦有两种形状，`||` 兜底是反模式，必须显式判 type；②前端渲染函数对 `s.tool` 缺失时应有兜底文案而不是裸 undefined。

## C3 · agent「偷懒」假象：自设 token 预算与网关固定注入冲突（2026-10-24，本批次最有价值的失败案例）

- **现象**：复合问题 agent 只执行 1 步就收尾，答案称「库存总值取证预算已用完，系统里没有记录」——表面看是模型不听指令、编造说法。同一问句在 passthrough 网关模式下正常两步取证，custom 模式下必现。
- **排查过程**（完整记录，体现方法）：
  1. 先怀疑 prompt 约束不够 → 加「1a 规则：每个子问题都必须取证」→ 无效；
  2. 再怀疑模型理解力 → 注入显式子问题清单（`_compound_hints`）→ 仍无效；
  3. 打印完整 trace 看 thought：第 2 步模型自述「**库存总值的取证预算已用完**」——它没偷懒，它真的被熔断了；
  4. 对照 usage 台账：custom 模式下每次 decide 的 prompt ≈ 8.5K token（网关自有提示词固定注入），而 agent 的 `DEFAULT_MAX_TOKENS=6000` 在第一次 decide 后即满足熔断条件，循环直接 break 进入「只准作答」收尾。模型在收尾 prompt 里看到「预算已用完」的说明，如实转述——于是产生了"编造没有记录"的假象。
- **根因**：token 预算保险丝的设计没有考虑网关侧固定成本（每请求 ~8.5K 人格前缀），6000 的默认值在本网关下等于"单步熔断"。passthrough 模式（~500/次）下永不触发，所以初期测试全绿——**环境差异掩盖了缺陷**。
- **修复**：`DEFAULT_MAX_TOKENS` 6000 → 40000，并注明"步数预算才是主约束，token 预算只是防失控保险丝，必须容得下网关固定注入"。
- **证据**：修复后同一问句三步完整取证（today_stats → stock_value → final），答案同时覆盖两个子问题（销售 0 元 + 库存 2651 元）；usage.jsonl 可见三次 decide 的 prompt_tokens 序列。
- **启示**：①"模型不听话"先查运行时约束（预算/超时/截断），再怪模型；②用量台账（usage.jsonl）是这类问题的决定性证据，值得单独建；③默认值要按"最差环境"（有固定注入的网关）校准。

## C4 · 会话状态三处不同步（2026-10-24）

三个相关小 bug，同一类根因——**会话状态（turns 数组）与控制状态（clarifying/correcting/clarifyCount 变量）分离维护，没有单一事实源**：

1. 「清空」按钮只重置 turns，不重置 clarifying/clarifyCount → 清空后新输入仍带旧草稿（用户气泡错误显示「修正」tag）。
2. 刷新页面后 sessionStorage 恢复了追问气泡，但 clarifying 未重建 → 补充回答被当成全新一单，丢草稿。
3. 澄清链走通后 clarifyCount 不归零 → 下一单可能被误跳过澄清。
- **修复**：exitClarify(done) 统一出口；loadConv() 扫描恢复澄清态；convClear 同步重置全部状态。
- **证据**：浏览器实测「清空 → 买了10瓶可乐」不再显示修正 tag；reload 后直接补「3块5一瓶」能出 ¥35 完整预览。
- **防御**：凡"会话可恢复"的功能，恢复函数必须覆盖全部派生状态；建议未来重构为单一 state 对象 + render。

## C5 · 网关"丢 system 角色"的真相追踪（2026-10-24）

- **现象（历史）**：自建网关下 LLM 无视 system 指令、返回闲聊，曾以 `merge_system`（system 并入 user）适配。
- **真相**：上管理面板排查——网关「系统提示词模式」配置为 `custom（网关自有提示词，避免指纹误报）`，即网关**主动替换**客户端 system 为自己的人格提示词。这不是协议缺陷，是部署配置。切 `passthrough` 后探针请求（system 指令"只回复 PASSTHROUGH_OK"）立即通过。
- **处理**：merge_system 保留为档案级开关（config.json），透传环境下关闭；网关按用户要求测完切回 custom（其目的为上游指纹规避），此时开关打开，行为不变。
- **衍生发现**：custom 模式每请求注入 ~8.5K token 人格前缀（passthrough 下同类请求 ~500）——16 倍固定开销，直接催生 C3。
- **证据**：面板截图（custom/passthrough 选项）；探针响应原文；usage.jsonl 中两模式的 prompt_tokens 对比（453 vs 8581）。

## C6 · 基础设施静默迁移：网关地址失联（2026-10-24）

- **现象**：本地 `.env` 指向的网关 `134.175.43.18:28466` 连接全部失败（HTTP 000），但无任何报错提示根因是"地址过期"。
- **真相**：网关已迁至 `111.91.30.23`（与 Talk2Stock 部署同机）；服务器上 Talk2Stock 的 `.env` 用 `localhost:7863` 同机直连，不受影响——只有本地开发环境的配置是旧地址。
- **修复**：本地两工作区 `.env` + worktree config.json 更新为新地址。
- **启示**：基础设施地址应集中单一来源；连接失败时输出可区分的错误（DNS 失败/拒绝连接/超时）而不是笼统 000。

## C7 · 单测自身的设计教训（2026-10-24）

- **案例 A**：模板兜底句重复拼接（4 次相同工具 → "库存 102 瓶；库存 102 瓶；…"）——mock 单测抓到的真产品 bug，`"；".join(notes)` 改为 `dict.fromkeys` 去重保序。
- **案例 B**：边界测试用例构造错误——想测 ">24 字交给 agent"，实际拼出恰好 24 字（不触发），断言失败才发现。教训：边界用例的期望值要显式计算（`25-7` 而非 `24-7`），并注释为什么是这个数。
- **证据**：tests/test_agent.py、tests/test_ask_rules.py 全绿记录。

## C8 · 优化了没有收益的场景：主数据预筛 vs 演示库规模（2026-10-25）

- **现象**：为实现 token 效率做了 _context_block 主数据预筛（全量名单 → 2-gram Jaccard 相关 top-K）。实测演示库上 parse prompt 1213 vs 预筛前 1279——**几乎没有差异**。
- **根因**：演示库主数据本来就少（3 供应商 + 3 客户 + ~8 商品 + 5 仓库 ≈ 50 token），全量塞入也不贵。预筛解决的是 120 商品上限的真实店铺场景——在演示数据上"优化了没有收益的场景"。
- **处理**：代码保留（规模化防护 + 单测覆盖 _rank_master），叙事不吹"预筛省 X%"；可测的 token 数字改用：①规则直答 0 token（高频问句免 LLM）；②解析链路 1359 token/单基线（eval 15 条实测）。
- **证据**：usage.jsonl 两模式对比；eval/results/run_20261025-001549-agentloop-smoke.json（15/15 全对、幻觉 0、延迟 2.09s/3.34s、tokens_total_avg 1359）。
- **启示**：先量化"这个场景的真实开销"再动手优化；防规模的优化要在文档里写明触发条件，不冒充当前收益。

## C9 · 外部真实批评点中的真问题：「一个配件多个规格，AI 不一定对得上」（2026-10-25，issue #1）

- **现象**：公开仓库收到 issue #1《AI 不是给穷人用的》。话糙，但技术判断里有真问题：「一个配件多个规格，AI 选择时不一定能一一对应上」。逐条对照代码，发现四个真实缺陷（不是演示数据能暴露的）：
  1. **解析层主动丢规格**：prompt v3 规则「items[].name 绝不能包含数字」会把「M8螺丝」剥成「螺丝」——与「主数据照抄」规则自相矛盾；
  2. **同名档案静默取第一行**：`find_material` 精确命中多条时直接返回第一条，「螺丝」两档规格（M8×20 / M10×30）会悄悄写到错的那档——最坏情况是错账，不是多点一下；
  3. **候选无上下文**：候选只给名字字符串，规格放在型号字段时用户只能瞎点；
  4. **评测集零多规格用例**：60 条语料无一条覆盖，等于「既没证明能，也没有反例」。
- **根因**：演示语料全是「可乐/纸箱」类无规格商品，规则与匹配层从未被规格场景测试过——**演示顺畅 ≠ 边界立得住**，issue 作者这一点说对了。
- **修复**（一次批次，全链路）：
  - 匹配层重写为纯函数（`match_material_rows`）：同名多档案 → `ambiguous` **绝不静默挑**；名字+型号+标准**合成串**匹配（`螺丝M8` 命中档案「螺丝 / M8×20」，括号/×x/大小写归一）；规格前置语序（`M8螺丝`）匹配不上时走候选，也绝不落错档；
  - 候选升级为 `{id,name,model,standard,unit}`，chip 显示「螺丝 · M8×20」；点选后 `items[].material_id` **直达档案**（闸门令牌天然覆盖该字段），手改名字即解除锁定；commit 对未消歧的同名明细做**写前预检**（不产生半截单）；
  - prompt v4：规格数字是名字的一部分（4 个反例锚定）+ 主数据名单带型号整串照抄 + 「各N」拆多行 + 多笔业务只处理第一笔（后一笔单价不搬）压 low；
  - 评测语料 v2 新增 spec 组 8 条（issue 场景），打分端配对升级（字符多重集等价 + gold aliases——模型把「M8螺丝」规范成主数据写法「螺丝 M8×20」是**正确**行为，该被记对）。
- **证据**：tests/test_material_match.py 20 项（全套 51/51）；eval spec 组 8/8 全对、幻觉 0、低置信标注准确落在 s07/s08（run_20261025-153108-promptv4-spec-final.md）；冒烟 15/15 无回归；浏览器全链路实测：裸「螺丝」→ 候选 chip 带型号 → 点选 M8×20 → 重预览「匹配→螺丝 M8×20」→ 写入单 00000000701 明细 barCode=BC633（= M8×20 档案 id）。
- **启示（对 Final failure analysis 有用）**：①负面反馈里技术点要逐条对照代码核实，别整段防御性反驳——本条 issue 四个技术点三个半是真的；②「演示顺畅」是选择偏差，边界要用对抗语料证明；③把外部批评转成冻结语料（spec 组 8 条永久进回归集），是最体面的回应。

## C10 · 新规则与旧清洗逻辑对抗：规格名被 `_clean_name` 剥掉（2026-10-25，边界审查抓到）

- **现象**：边界审查探测中「向美宜佳采购6号电池60节」解析出 name=「号电池」——prompt v4 刚立了「型号规格必须保留」的规矩，`normalize` 里的旧兜底 `_clean_name` 却在剥它。
- **根因**：前缀正则 `^(\d+)(量词)?(.+)$` 的量词是**可选组**——「6号电池」被当成「6 个号电池」剥掉数字；同型受害者：304不锈钢管→不锈钢管、2.5平方电线→平方电线、4分PPR管→分PPR管。**spec 组 8/8 当时能过纯属模型输出形态恰好绕过**（模型把数量拆进了 qty 字段、name 没触发兜底路径），回归测试没暴露是因为测的是「模型没犯错」的形态，不是「模型犯了错」的形态。
- **修复**：量词改必选——「数字+量词」（3瓶可乐 / 电池100节 / 2.5平方电线100米）才算数量剥掉；数字直接黏名词一律保留。UNITS 补 节/盒/把/双/对/捆/扎/提/副（「电池100节」「12盒方便面」此前该剥没剥）。
- **证据**：tests 12 项清洗矩阵（59/59 全绿）；端到端重跑「6号电池60节」name 完整；spec 组复跑 8/8（run_20261025-163112-audit-clean-name）。
- **启示**：**改规则时必须全局搜同语义的旧实现**（一个「名字不带数字」的意图散落在 prompt 和正则两处，改一处漏一处就是对抗）；兜底逻辑的测试用例要包含「上游已正确时不触发」和「上游出错时触发」两种形态。
