# 失败案例与踩坑记录（failure analysis 素材）

> 课程评分明文要求 failure analysis；本文件按时间序记录 agent 升级过程中的真实失败、
> 根因与修复，全部来自真机实测（8091 开发实例 + 网关面板），可作为报告与答辩证据。
> 每条格式：现象 → 根因 → 修复 → 状态。

## 2026-10-24

### F1 规则直答截胡复合问题（P1，已修复）
- **现象**：「今天卖了多少？另外库存的货总共值多少钱？」被第 1 层规则直答命中 `today_stats`，只回答了一半。
- **根因**：规则直答层只按意图正则匹配，没有复合意图护栏。
- **修复**：双护栏——句长 >24 字、含「另外/还有/顺便/然后/同时」等连接词的一律放行给 agent loop；单测补 2 个用例。
- **延伸**：即便进了 loop，模型仍会只查一半就 final（见 F5），最终用显式子问题清单注入解决。

### F2 SSE 事件字段错位 → 前端渲染 `undefined`（P0，已修复）
- **现象**：步骤行显示「✓ undefined」，展开区空白。视觉模型评审一眼抓出（用户看到直接失去信任）。
- **根因**：后端把 step 记录直接平铺进事件（`{"step": 1, "tool": ...}`），前端却按 `{"type":"step","step":{...}}` 解包，`ev.step` 取到步序号 1，`s.tool` 自然 undefined。
- **修复**：统一事件信封 `{"type":"step","step":rec}`；教训是**事件契约要先写下来再两端实现**，且首测就该截图而非只看 DOM。

### F3 网关 custom 模式每次请求注入 ~8K token 自有提示词（P2，已知悉，待定夺）
- **现象**：同一 agent 决策步骤，custom 模式 prompt 8388 token vs passthrough 518 token，差 16 倍。
- **根因**：WorkBuddy2API「系统提示词模式=custom」时把 /app/prompt.txt 注入每个请求（为避免上游指纹误报）。
- **修复**：无代码问题；测完已按约定切回 custom。**待用户定夺**：正式环境切 passthrough（省 token 但失去网关自有提示词的防误报作用）或保持 custom（token 免费期内无成本）。

### F4 录单澄清两个状态 bug（P1，已修复）
- **现象①**：澄清追问后刷新页面，再输入被当成全新一单（丢草稿）。
- **根因①**：`loadConv()` 恢复会话流但不重建 `clarifying` 状态。
- **现象②**：会话「清空」后再输入仍带着旧草稿（对话流出现莫名的「修正」标签）。
- **根因②**：`convClear` 只清 `turns`，不重置 `clarifying`/`correcting`。
- **修复**：loadConv 自愈重建澄清态；清空时 `exitClarify(true)` 一并重置。

### F5 agent 复合问题偷懒：只查一半就作答（P1，已修复）
- **现象**：「今天卖了多少？另外库存值多少钱？」模型查完 today_stats 就 final，声称「库存总值未取到，系统里没有本次查询记录」。
- **根因**：LOOP_PROMPT 的规则约束（1a 条款）不足以改变行为——实测两次均只调 1 步。
- **修复**：把复合问题按连接词拆成显式子问题清单注入 goal（`_compound_hints`），每个子问题必须先取证。**有效性待回归验证。**

### F6 模型对不存在的工具编造「查不到」措辞（P2，记录在案）
- **现象**：问「雪碧」（库里没有），模型第 3 步调用了尚未实现的 `search_history`，收到「没有这个工具」报错后，final 却说「历史单据同样查不到」。
- **根因**：数字接地校验只拦**数字**幻觉，拦不住这种定性措辞的过度引申。
- **处置**：Phase 2 实现 search_history 真工具后此坑自动消失；答辩可作为「接地校验边界」的诚实案例。

### F7 模板句兜底重复拼接（P3，已修复）
- **现象**：预算耗尽兜底时，同一工具的模板句重复 4 次（「库存 102 瓶；库存 102 瓶；…」）。
- **修复**：`dict.fromkeys(notes)` 去重保序。单测 `test_total_failure_returns_template` 抓到的。

### F8 .env 网关地址失效（P2，已修复）
- **现象**：本地 curl 网关 HTTP 000。
- **根因**：`.env` 里 `T2S_BASE_WORKBUDDY` 还是旧机 134.175.43.18，网关实际已迁 111.91.30.23（服务器侧用 localhost:7863 不受影响）。
- **修复**：本地两份 .env + config.json base_url 同步更新。

### F9 视觉评审抓出的密度/对比度问题（P3，已修复）
- 进行中状态 2.2:1 对比度（近隐形）→ 深绿 12.5px + 金点扩散环；气泡两态宽度跳变 → min-width:300px；展开区间距过松 → 压缩至 8-12px 档。
- **方法论收获**：截图 + 独立视觉评审（子代理/视觉模型）能抓住纯 DOM 数值测不出的问题，与项目既有「必须真截图」偏好一致。

### F10 问答答不了预置工具之外的问题 + 推理模型思考失控（P1，已修复）
- **现象**：「有多少个供应商」答不上来；agent 在 recent_bills / debts /
  search_history 里空转，4 步走完仍超时；有时单步决策 120s+ 或返回空正文。
- **根因**：① 工具箱只有 9 个窄工具，没有任何主数据/全库查询能力，模型无
  可用工具只能乱试；② 推理模型在长 prompt 的 JSON 决策上烧 9k~13k token
  思考，网关默认不设输出上限。
- **修复**：`sql_query` / `db_schema` 全库只读工具 + 动态 schema 注入；主数据
  计数规则直答；`llm.agent_model` 把决策切到低延迟模型；表结构只在首轮
  注入；单轮决策失败不再直接返回错误，而是作为观察喂回重试，步数耗尽仍
  可用工具模板句兜底。

## 2026-11-09

### F12 线上问一问决策模型被 agent_model 覆盖，「用的什么模型」口径对不上（P2，已修复）
- **现象**：admin 已把共享档案切到 `global:hy4free`，`/api/ask` 的 meta.model 却一直显示 `global:default-model`——答辩问「线上用的什么模型」时与设置页口径矛盾（服务器真机 + 网关回显实测定位）。
- **根因**：F10 修复时把 `llm.agent_model` 配成了 `global:default-model`（决策专用低延迟模型），`agent_profile()` 用它覆盖档案模型；这个覆盖对「默认跟随 admin 全局设置」的产品语义是隐形的。
- **修复**：①线上 `agent_model` 清空（服务器备份 `config.json.bak-20261109-hy4`），决策跟随全局；②agent 决策步默认附 `reasoning_effort=low`（档案显式设置优先）——用参数控制思考深度，替代「另配一个决策模型」的粗粒度隔离，与 `agent_max_tokens` 输出封顶互补；③档案级新增 `reasoning_effort` / `extra_body`（Qwen enable_thinking、Claude thinking 等厂商私有参数透传，厂商叫法不一时走后者），设置页共享/我的模型两个表单均可配，端点不认的参数 400 一次后自动摘除（同 stream_options quirk 先例）。单测 9 条（tests/test_llm_reasoning.py）。
- **教训**：「决策用哪个模型」这类横切配置，meta 里必须可见且与设置页口径一致——否则答辩/审计场景第一句就被问倒。

### F11 分仓库存查问：仓库过滤精确匹配查空 → 误报「没有库存记录」（P1，已修复）
- **现象**：「可乐在原料仓库还有多少？」（比档案名「原料仓」多一个字）→ depot 过滤归一化精确匹配查空 → 答「可乐在系统里没有库存记录」——货明明有库存，属误导性错误答案（评审视角下比崩溃更伤信任）。
- **根因**：`_stock_query` 自行用 `_norm` 相等过滤仓库，没走 `find_depot` 的模糊匹配；且查空后的措辞模板不区分「无此仓」与「无库存」。
- **修复**：`erp.py` 抽纯函数 `match_depot_rows`（exact + **双向包含**：「原料仓库」也能命中「原料仓」；多命中交上层，绝不静默挑第一个）；`_stock_query` 改走 `find_depot`，查无此仓时明说「没有叫 X 的仓库」并按编辑相似度给相近候选；单测 9 条（`tests/test_depot_match.py`，含「误导句不许再出现」断言）。
- **状态**：已修复，单测过；真机回归待本地 ERP 容器恢复后跑一次黄金数据（原料仓 50 / 成品仓 52 / 总 102）。
