# 功能补齐批次（2026-11-25）：从「演示级」到「可交付业务闭环」

> 触发：一份外部功能架构评审提出 14 项问题。逐条核对当前 main 后，8 条成立、
> 2 条为事实错误（退货已有、缓存已失效）、4 条只对一半。本批次只落地真正
> 会造成错误业务决策或安全缺口的 6 项；交互状态机类（跨单追问、歧义会话态、
> 草稿版本栈）留待单独一批，避免与未提交的 ask/llm 改动冲突。

## 一、本批次改动

### 1. 采购建议扣减在途采购量（P0）

问题：旧公式 `建议量 = 目标库存 − 当前库存`，完全不看「已下单未入库」的采购
订单。昨天刚下单 500 件、今天再跑算法，仍会建议再买 500 件，直接制造超采购。

实现：
- `app/core/procurement.py` 新增 `_SQL_PENDING`：`jsh_depot_head`（`type='其它'`、
  `sub_type='采购订单'`、`status IN ('1','3')` 即已审核/部分采购）join 明细，
  减去 `jsh_depot_item.link_id` 已关联入库的数量；没有 link_id 的老数据按未入库
  计（保守，宁可少扣也不把已到货当在途）。
- 公式改为 `A = 库存 + 在途`，`建议量 = ceil(max(0, 目标 − A))`；分级、可支撑
  天数、理由句同步用 A；行级新增 `pending_qty` / `available`。
- 在途查询单独降级：旧库缺字段时整份建议照常出，`assumptions` 显式写
  「在途采购查询不可用，未扣减」；取证清单新增一行「在途采购（未入库订单）」。
- 看板采购卡显示「在途 X」，表格库存列加在途小字。

验证：`tests/test_procurement.py` 新增 2 例（在途 100 件使建议量 95→0 且等级
reorder→ok；查询失败时建议量回到 95 且 assumptions 含降级说明），12 项全绿。

### 2. 业务防重（P1）

问题：Nonce 只防同一张卡片双击，防不了两个业务员先后口述同一笔业务——两笔
应收/出库会真实落地。

实现：新增 `app/core/dedupe.py`。
- 窗口 30 分钟，按 `create_time`（入库时间，不受用户手填 oper_time 影响）。
- 判定：同业务类型 + 往来单位归一相同 + 至少一条商品名归一相同 + 数量一致或
  相差 ≤10%；任一方为空不判。
- 出卡时 `preview.duplicate` 带 `{hit, matches[number/time/party/hits]}`，确认卡
  显示黄条与原单号；不阻断提交。
- 45 秒进程内缓存；写入成功后 `invalidate()`，避免刚提交的单被判成历史重复；
  数据库不可达返回 `skipped`，绝不让防重拖慢录单。

验证：新增 `tests/test_dedupe.py` 6 例（命中/数量容差/不同单位商品/非单据类型/
查询失败降级/缓存与失效），全绿。

### 3. 会话令牌可吊销（P1，安全）

问题：30 天无状态 HMAC 令牌，员工离职或设备丢失后只能改全局密钥（全员掉线）。

实现：
- `auth.py` 令牌 payload 增加 `ep`（吊销代数），校验时 `ep < 当前代数` 即拒绝。
- `bump_epoch(login)` 将代数 +1 落盘 `data/session_epoch.json`（0600、原子替换、
  1 秒缓存）；旧令牌无 `ep` 视为 0，兼容存量。
- `POST /api/auth/logout`（当前登录名）、`POST /api/auth/revoke`（管理员指定
  login）；前端两处登出入口统一走 `endSession()`，先吊销再清本地。

验证：`tests/test_auth.py` 新增 4 例（登出后同登录名全部旧令牌失效、按 login
隔离、缓存重置后仍失效、空 login 无操作），认证相关 30 项全绿。

### 4. 批量写入失败可恢复（P1）

问题：批量提交逐单写，第 3 张失败时前两张已落库；前端只标红，重试复用旧令牌
（已被闸门消费）必然再失败。

实现：`common.js`
- 重试条件由 `b.dirty` 改为 `b.dirty || b.state === 'failed'`——失败单重试前
  强制 `/api/resolve` 换新令牌。
- 卡片结果区显示失败原因 + 「重试本单」按钮；已写入卡片显示单号 + 「生成退货
  单（冲销本单）」按钮。

### 5. 反向单据草稿（P1，业务闭环）

问题：系统只做加法，缺「客户退货/采购退回/录错冲销」入口。注意：退货单本身
一直支持（`purchase_return` / `sale_return`），缺的是从已写入单据一键生成反向单。

实现：
- 新增 `app/core/reverse.py`：采购入库 ↔ 采购退货、销售出库 ↔ 销售退货；数量/
  单价/往来单位/仓库原样保留，备注带原单号；其它类型拒绝。
- `POST /api/bill/reverse`：原单草稿 → 反向草稿 + 预览 + 一次性令牌，只出卡不写库。
- 前端在已写入卡片上一键生成，作为新卡追加到当前批次，仍需人工确认。
- 原单保持不动，账目由正负两笔抵消，审计链完整。

验证：新增 `tests/test_reverse.py` 5 例（四向对调、字段保留、非法类型、空明细、
备注截断），全绿；接口冒烟返回中文拒绝文案。

### 6. 看板单据总数改精确计数（P2，口径诚实）

问题：`all_bills()` 受 ERP 列表翻页限制，`bill_count` 是样本数不是总数。
注意：欠款合计早已 SQL 全量聚合（ADR-13），财务核心不受影响。

实现：`report._bill_total_sql()` 直查 `COUNT(*)`；`/api/dashboard` 返回
`bill_total`；前端显示精确总数，DB 不可达时退回样本数并标注「（REST 样本）」。

## 二、明确不做的项

| 评审项 | 判断 | 原因 |
|---|---|---|
| 「没有任何退货/红冲功能」 | 事实错误 | `purchase_return`/`sale_return` 一直可用；本批次补的是「已写入单据 → 反向单」入口 |
| 「60 秒缓存导致写后读脏读」 | 事实错误 | commit 后 `erp.invalidate("")` 同时清 list 缓存与 `_stock_tbl` |
| 「下线 sql_query」 | 方向相反 | 问一问的自由问答靠它；正确做法是表白名单 + 审计（已有只读事务护栏） |
| 跨单追问 / 歧义会话态 / 草稿版本栈 | 成立但延后 | 需要改对话状态机，与当前未提交的 ask/llm 改动冲突，单开一批 |
| 视觉解析 OCR 兜底 | 成立但延后 | 项目承诺零第三方依赖，引入 OCR 引擎是架构决策，不是补丁 |

真实库验证（本地 erp-mysql，117 张历史单据 + 临时插入后删除）：

- 采购在途：插入采购订单 100 件 → `pending_qty=100`、`suggest 8→0`、
  等级 `reorder→ok`、理由句「在途 100，可支配 152」；再插入关联入库 60 件
  （`jsh_depot_item.link_id` 指向订单明细）→ 在途剩 40，抵扣分支正确。
- 防重：插入近 30 分钟销售单（organ_id=177，可乐×50）→
  `/api/resolve` 返回 `duplicate.hit=true` 并带原单号；数量 500 不命中。
  **真实库暴露过一个单测抓不到的 bug**：初版 SQL join 了不存在的
  `jsh_customer` 表（jshERP 客户存在 `jsh_supplier`，type='客户'），防重会
  静默降级；已改为按 `organ_id` 精确过滤，不依赖客户表名。
- 反向单：`/api/bill/reverse` 成功分支返回 `sale_return` 草稿，明细/仓库/
  金额保留，`errors=[]`，令牌已签发。
- 前端：真实浏览器注入确认卡，黄条「疑似重复录入：近 30 分钟已有
  TEST-DUP-…（…可乐×50）」正常渲染。
- 旧令牌兼容：手工构造无 `ep` 的 v2 令牌 → `verify_session` 通过（存量登录无感）。

未跑：线上 ERP 的采购订单数据（本地库无采购订单，已用临时数据验证 SQL 语义）；
部署后线上 `/api/procurement/suggest` 首次调用时确认 `evidence` 出现「在途采购」行。
