# 证据索引（写报告 / 答辩时的留痕地图）

> 原则：课程评分要的 "documented prompts, workflows, iterations and tool choices" 和
> "success criteria defined before testing"、"failure analysis"，全部要能拿出**可回溯的实物**。
> 本文档记录每类证据在哪、怎么再生成。运行时日志在 `app/data/`（gitignore，本机留存），
> 不可变快照在 `eval/results/`（随仓库提交，组员都能看）。

## 一、评测与迭代留痕（已入库）

| 证据 | 位置 | 说明 |
|---|---|---|

## 二、写入闸门取证（快照已入库：`eval/results/gate-audit-snapshot-20261010.jsonl`）

| 事件 | 对应 audit.jsonl 记录 |
|---|---|
| 无令牌直接 commit → 拒 | `commit_rejected`（source: curl-attack）×1 |
| 伪造令牌 → 拒 | `commit_rejected`（curl-attack）×1 |
| 确认后篡改草稿 → 拒 | `commit_rejected`（e2e-test，reason: 草稿在确认后被改动）×1 |
| 令牌重放 → 拒 | `commit_rejected`（e2e-test）×1 |
| 正常确认 → 写入成功 | `commit_ok`（单号 00000000682，含原话/模型/prompt 版本 hash） |
| 持续取证 | 运行时 `app/data/audit.jsonl`（每张写入的单、每次被拒的尝试）；用户改过的字段自动沉淀 `app/data/regression.jsonl` |

**答辩话术**："未经确认的写入为 0"不是口头承诺——闸门把每次拒绝都记了账，快照里 4 条 `commit_rejected` 就是证据。

## 四、git 提交历史即迭代留痕

`git log --oneline` 本身就是分工与时间线证据；每条提交信息写清"为什么"。
建议：组员一律走 feature 分支 + PR（见 `CONTRIBUTING.md`），PR 描述里写"改了什么、为什么、怎么验证的"，
这些 PR 记录在终版报告里就是协作与迭代的原始凭证。
