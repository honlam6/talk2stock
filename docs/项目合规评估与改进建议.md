## 0. 一句话结论

**选题与提案高度吻合，工程完成度也远超"开题阶段"应有的水平（已有一个能跑的三入口原型）；但它现在是一份"很好的工程"，还不是一份"很好的课程项目"——因为课程 45% 里权重最高的三块（可打开的真实链接、带基线的评测证据、GenAI/应用分层架构与迭代留痕）目前几乎为零，且提案自己承诺的几项关键能力（只读问答、审计日志、候选匹配、写入闸门的不变量）尚未落地。**

按现状直接交，中期报告最多拿到 Feasibility 的部分分、Evidence 基本为 0；终版报告的 "Results & Analysis 5 分" 和 "Technical Implementation 5 分" 会大面积失分。

## 3. 与提案的一致性：承诺 vs 实现（逐条核查）

提案里写得越具体、越像"设计亮点"的地方，越会被老师拿来对照。逐条核对结果：

| # | 提案承诺 | 代码现状（证据） | 状态 |
|---|---|---|---|
| 1 | 三层架构：入口层 / 模型层 / 落库层，职责切开 | `server.py`(入口) + `core/llm.py`(模型) + `core/draft.py`(草稿/落库) + `core/erp.py`(ERP 客户端) | ✅ 落地 |
| 2 | 一句话生成单据草稿 | `POST /api/parse` → `llm.parse()` → `draft.resolve()` | ✅ |
| 3 | 意图分类：采购入库 / 销售出库 / 退货 / **库存查询** | `BILL_TYPES` 6 类业务（含退货）；**"库存查询"意图未实现** | ⚠️ 部分 |
| 4 | 口语解析：数量单位、价格含税口径、日期 | `SYSTEM_PROMPT` + `normalize()` + `_to_num/_clean_name`（含"3块5"→3.5） | ✅ 基本 |
| 5 | 主数据匹配：**别名表 + 模糊匹配；多候选列前三给人点** | `find_party/find_material` 只有 精确→归一→子串包含；**多候选直接返回 `None`（`erp.py:186-189`），无候选列表、无别名表、无 embedding** | ❌ 缺 |
| 6 | 档案补齐草稿：预填编码/单位/换算/默认仓库，绝不自动写 | `resolve()` 返回 `to_create`；但 `commit()` 只按**名称**新建，未预填编码/换算/默认仓 | ⚠️ 部分 |
| 7 | 落库层写入闸门："没有人工确认事件的写入请求一律拒绝" | 写操作只在用户点"确认写入"后触发；但 **`/api/commit` 服务端不校验任何确认令牌**，直接 POST draft 即可写库 | ⚠️ 形式有、机制无 |
| 8 | 审计记录：原话 / 模型 / 提示词版本 / 确认人 / 改动字段 | **全库 grep 无 audit/审计/日志落盘** | ❌ 缺 |
| 9 | 确认卡：每个字段标明来历（抽取/匹配/默认/建议新建） | `common.js:showPreview()` 有 "已有 / 将新建 / 匹配→X" 标签；但**系统默认值（默认仓、默认日期）不标注来源** | ⚠️ 部分 |
| 10 | **只读问答**（库存/补货，agent 自己调工具） | **无 NL 问答接口**，只有静态 `dashboard.html` + `/api/dashboard` | ❌ 缺（MVP 项） |
| 11 | 语音输入 | 无 | ❌ 缺 |
| 12 | 箱/件单位换算归一 | `ensure_unit()` 建单位时 `ratio=0`，无主/辅计量换算逻辑 | ❌ 缺（提案自认的高危失败点） |
| 13 | 含税/未税口径 | `draft`/`create_bill` 无 taxRate / 含税字段 | ❌ 缺 |
| 14 | 用户改过的字段沉淀成回归测试集 | 无 | ❌ 缺 |
| 15 | 自建为主，不绑 Dify | 纯标准库 Python，零第三方依赖 | ✅ |
| 16 | 只通过 ERP 官方接口写入，不碰数据库表 | `core/erp.py` 全部走 REST | ✅ 强（可自证） |

**结论：提案里"三层架构 + 自建 + 只走官方接口"这三条最核心的承诺都落地了，含金量高；但 4 个被提案自己点名为"设计亮点"的能力（写入闸门不变量、审计日志、候选匹配、只读 agent 问答）没实现——而它们正是老师最可能追问的点。**

## 4. 必须立刻处理的风险

### 4.1 🔴 安全：`app/config.json` 里是明文真实密钥
文件内曾明文存放 3 组真实凭据（WorkBuddy / ModelScope / DeepSeek 各一把 Key，此处不再复述明文），外加 ERP 默认口令 `jsh/123456`。

一旦把 demo 链接公开、或把仓库推到 GitHub，等于直接泄露 API Key（会被扫号盗刷）。**且当前 `/api/config` 会把脱敏后的 key 返回给任何访问者，`/api/commit` 无任何鉴权——任何拿到链接的人都能往 ERP 里写单。**

必须做：
- 把密钥改从环境变量读取（`os.environ`），`config.json` 只留占位符，并加入 `.gitignore`；
- 公开 demo 前给 `/api/commit`、`/api/config/*` 加一个演示口令（最简单的 Basic Auth 或一次性 token）；
- 若已有密钥进过 git 历史，**轮换这三把 key**。

### 4.2 🔴 可行性：系统现在打不开
`curl http://localhost:9999/jshERP-boot` 返回 **502**，`docker ps` 无容器——ERP 没起。Interim 的 4 分 Feasibility 明确要求 "the link works when we open it"。提案自己也提出：大陆服务器要 ICP 备案来不及，需在 **IP+端口 或 海外节点** 里二选一。这件事必须在 11-01 前解决，且要提前测通（含 HTTPS 证书、演示账号、冷启动时间）。

### 4.3 🟡 sponsor 与真实语料仍未落实
提案第八节承认 sponsor、真实数据规模、"一张单实际录多久"都还是待确认项。Business 要求 "a real user or your sponsor confirmed the problem, and say what you changed as a result"。没有这一条，Business 1–2 直接空。**本周必须把联系人落实**（哪怕先找一个校内小商户/家人公司做 proxy user，课程允许 credible proxy user）。

### 4.4 🟡 开源协议口径不一致
提案已记录：Gitee 标 Apache-2.0，部分文章写 GPL-3.0。**必须以实际部署 commit 里的 LICENSE 文件为准，并把结论写进报告**（这是加分项——体现严谨）。顺手做掉：`jshERP-deploy/LICENSE` 就在仓库里，直接读。

## 5. 改进路线图

### P0 — 今晚到明天（保 Project Plan）
1. **把 9 页中文选题建议压成 2–3 页英文 Project Plan（课程模板）**，必含：Group ID、6 人姓名/学号/专业、角色分配表、sponsor（可先填 proxy user 并注明）、范围（做什么/不做什么）、时间线、评估计划。
2. 顺手把 `LICENSE` 结论、以及"待确认项"清单固化进计划书附录。

### P1 — 到 11-01 中期（保住 10 分里的 Evidence 3 分）
3. **建评测资产（性价比最高的一件事）**：
   - 60 条冻结语料（30 自写口语句 + 20 sponsor 真实消息(脱敏) + 10 条对抗样本）；
   - 一个 `eval/run.py` 打分脚本，输出整单关键字段全对率、字段级准确率、幻觉字段数、未确认写入数；
   - **三组基线**：① jshERP 原生界面手工录单（3 人计时、记字段错误数、记被迫新建档案次数）；② 去掉确认闸门直写库 20 条；③ 去掉主数据检索。
   - 这一步直接把 Interim Evidence(3) + Final Results(5) 一起拿下。
4. **审计日志**：`commit()` 时向 `app/data/audit.jsonl` 追加一条（原始话术、模型名、`SYSTEM_PROMPT` 的 hash、时间戳、draft 与最终写入的 diff）。提案承诺的，也是"闸门"能自证的关键。
5. **写入闸门加固**：`/api/resolve` 签发一次性 `confirm_token`，`/api/commit` 校验——把"无确认不写入"从 UI 约定升级为服务端不变量。**这正是提案说"最想让老师看到的设计点"，现在其实没实现。**
6. **部署 + 备份录屏**：ERP 起容器，壳子部署到公网可达地址，录一段端到端 demo。
7. **只读 agent 问答**：新增 `/api/ask`，用 tool calling 调只读函数（库存查询、低库存、动销、欠款），对应提案的"放开让 agent 自己调工具"。

### P2 — 到 12-20 终期
8. **主数据候选匹配**：多候选时返回 top3 让用户点选 + 别名表（先规则/编辑距离，embedding 可选）。
9. **单位换算**：主/辅计量 ratio（箱↔瓶），并在评测口径里做归一。
10. **含税/未税口径**：draft 增 taxRate / 含税价字段。
11. **失败案例分类 + 回归集**：把用户改过的字段自动沉淀为回归用例（提案承诺项）。
12. **架构图 + 迭代留痕**：一张图（GenAI 层 + 应用层 + ERP 层），`SYSTEM_PROMPT` 版本化并记录"每次改动 → 评测变化"。
13. **用户测试**：两轮、5 人、每人 10 条、边做边说，配 SUS 量表。
14. **复现文档 README**：docker 起 ERP → 起壳子 → 配模型 → 跑自检 → 跑评测，一条命令能复现。

## 7. 值得保留的既有优势（别在改的过程中弄丢）

- **问题界定极扎实**：统计局第五次经济普查数据、用友/简道云/象过河的实操文档交叉验证，"不是 ERP 天生慢，而是档案修复成本 + 翻译成本"这个界定比"ERP 慢"精准得多，是 Final "Problem Definition & Innovation 5 分"的强项。
- **成本测算给算式不给结论**：780 万输入 / 120 万输出 token → qwen-turbo ≈3 元、qwen-plus ≈9 元，基准 250 元 / 最坏 1050 元，人均 42–175 元。这种"可验证的量化"是加分项。
- **三层架构 + 只走官方接口不碰数据库**：可自证、可审计，工程上是对的。
- **三入口共用一套 `resolve/commit`**：不会出现"两套逻辑两种行为"，设计干净。
- **`docs/` 里的 API 实测清单**（339 端点、失败端点及替代路径、必填参数坑）：这是很硬的工程证据，复现文档可直接引用。
