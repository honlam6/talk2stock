# Talk2Stock 架构决策记录（ADR）

> 本文件记录 Agent 升级批次（feature/agent-loop，2026-10）的关键架构决策：
> 每条含背景、备选方案、取舍理由、被否决的原因。配套的运行时失败证据见
> `docs/失败案例与迭代证据-agent升级.md`。

## ADR-1 · 手写 function-calling 循环，而非 OpenAI tools 协议

**背景**：问答要支持复合问题（「上月谁买得最多？他欠我多少？」），需要多步工具链。

**备选**：
- A. OpenAI function-calling（`tools` 参数 + `tool_calls` 返回）
- B. 手写 JSON 动作循环：LLM 输出 `{thought, tool, args}`，observation 回喂（**选定**）

**理由**：
1. 目标部署环境的端点协议支持参差（自建网关有替换 system、吞参数等行为），
   应用层循环对任意 OpenAI 兼容端点行为一致；
2. 每步 trace（thought/args/observation/耗时/token）天然可落盘，审计与前端
   回放不需要解协议层对象；
3. 预算控制（步数 + token）在应用层实现，与协议无关。

**代价**：动作 JSON 偶发畸形（靠 `_extract_json` 平衡括号剥离 + 错误观察回喂自愈）；
不享受协议层的工具调用微调红利。对 3-4 步的短链路场景，实测影响可忽略。

## ADR-2 · 三层问答路由：规则直答 → agent loop → 模板兜底

**决策**：高频无参数统计问句（今天卖了多少/谁欠我钱/什么货快没了）用正则
确定性直连只读工具，**0 token**；未命中走 agent loop；LLM 作答必须过数字
接地校验，不过退模板句。

**理由**：高频问句的答案完全由确定性函数给出，LLM 参与只增加成本、延迟与
幻觉面；接地兜底保证最坏情况下的答案仍可追溯。

**护栏**（实测教训 C1）：规则准入必须双护栏（句长 ≤24 + 无复合连接词），
否则「今天卖了多少？另外库存值多少钱？」会被截胡只答一半。

## ADR-3 · 结构化数据 tool-use，非结构化 BM25 —— 而非全场景 RAG

**决策**：库存/欠款/采销等结构化问答走工具调用 + 数字接地；操作文档与历史
单据检索走纯标准库 BM25（中文 bigram 分词）。

**否决向量 RAG 的原因**：
1. 结构化数字经检索块转述会丢精度且不可审计，违背「答案可追溯到 ERP 真实值」
   的项目承诺；
2. embedding 依赖外部 API 或本地模型，与「纯标准库自建、可离线」承诺冲突；
3. 文档/历史语料小（百级块），BM25 的可解释命中（相关度分数）比语义检索
   的黑盒相关性更符合课程评审的可验证性要求。

**诚实记录**（C8）：BM25 的价值在文档/历史增长后体现；当前演示库收益小。

## ADR-4 · 写入闸门用 HMAC 无状态令牌 + 持久化 nonce 黑名单

**决策**：confirm_token = base64(payload).HMAC，payload 含草稿哈希/过期/nonce；
一次性由 `data/used_tokens.jsonl` 黑名单保证（TTL 窗口自动清理）。

**替代了**：内存 dict（原实现）——服务重启全部待确认令牌失效、多进程部署
（gunicorn 等）不可用。

**取舍**：meta（原话/模型等审计上下文）随令牌自描述，token 变长（数百字节）
但换来自描述与跨进程可验；黑名单每 commit 追加一行，量级可忽略。

## ADR-5 · 主动澄清用规则检测而非 LLM 自判

**决策**：澄清触发条件（无明细/无数量/无往来单位/无单价）由确定性规则产生，
不花 LLM；澄清问题文案也是模板。用户补充回答复用既有多轮修正链路
（prev_draft 随输入回喂）。

**理由**：澄清的判断条件是结构性的（字段有无），LLM 自判反而引入不确定；
一条链路两种用途（修正/澄清补充），架构上零新增状态机。

**上限**：2 轮，超限自动 skip_clarify 出确认卡——防止无限追问烦人。

## ADR-6 · token 预算是防失控保险丝，步数预算才是主约束

**决策**：`DEFAULT_MAX_TOKENS = 40000`（远大于单步消耗）。

**教训来源（C3）**：曾设 6000，在网关 custom 模式（每请求固定注入 ~8.5K
人格提示词）下第一次 decide 后即熔断，模型被迫「预算已用完」式收尾——表面
是模型偷懒，实际是自设预算与网关固定成本冲突。保险丝的阈值必须按
「最差环境（有固定注入的网关）」校准。

## ADR-7 · SSE 流式过程展示（action 事件先于工具执行）

**决策**：`/api/ask/stream` 事件序 start → action（决策出工具、执行前）→
step（trace 落定）→ done。action 事件让前端在工具执行时即显示
「正在查询库存…」，而不是等执行完才补历史。

**实现约束**：纯标准库 `http.server` 下以 `Connection: close` 界定响应结束；
前端 fetch + ReadableStream 解析（EventSource 不支持 POST）；流式不可用时
自动降级普通一次性接口（老 WebView 保底）。

## ADR-8 · 用量计量：能精确则精确，不能则估算并标注

**决策**：流式请求带 `stream_options.include_usage`（网关 400 一次后记忆
降级），非流式读响应 usage；都拿不到按字符估算（×0.8 系数）且
`estimated: true` 落盘。每次调用（含 agent 每步、洞察一跳）都记
`data/usage.jsonl`，分 purpose 聚合。

**理由**：token 效率叙事必须有真实台账支撑；估算值不标注会污染对比实验
（C3 的排查正依赖台账的精确值区分网关固定注入）。
