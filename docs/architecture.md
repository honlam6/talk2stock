# Talk2Stock 架构决策记录（ADR）

> 本文件记录 Agent 升级批次（feature/agent-loop，2026-10）的关键架构决策：
> 每条含背景、备选方案、取舍理由、被否决的原因。配套的运行时失败证据见
> `docs/失败案例与迭代证据-agent升级.md`。

## ADR-1 · 手写 function-calling 循环，而非 OpenAI tools 协议

**背景**：问答要支持复合问题（「上月谁买得最多？他欠我多少？」），需要多步工具链。

**备选**：
- A. OpenAI function-calling（`tools` 参数 + `tool_calls` 返回）
- B. 手写 JSON 动作循环：LLM 输出 `{thought, tool, args}`，observation 回喂（**选定**）

**理由**：
1. 目标部署环境的端点协议支持参差（自建网关有替换 system、吞参数等行为），
   应用层循环对任意 OpenAI 兼容端点行为一致；
2. 每步 trace（thought/args/observation/耗时/token）天然可落盘，审计与前端
   回放不需要解协议层对象；
3. 预算控制（步数 + token）在应用层实现，与协议无关。

**代价**：动作 JSON 偶发畸形（靠 `_extract_json` 平衡括号剥离 + 错误观察回喂自愈）；
不享受协议层的工具调用微调红利。对 3-4 步的短链路场景，实测影响可忽略。

## ADR-2 · 从规则直答路由到统一业务 Agent（2026-11-20 修订）

**历史决策（保留为演进证据）**：高频无参数统计问句由正则直连确定性工具，
0 token；其余走 agent loop；接地失败退模板句。该方案适合早期「只读问答」，
但当问一问和录单被要求合并为唯一入口后，规则抢占会让大量用户请求绕开
模型的意图理解与纠错能力。

**当前决策**：主入口统一走 `run_agent`。规则函数不再决定路由，而是作为
`today_stats/month_stats/debts/...` 等确定性工具供模型调用。新增
「回答检查」步骤：final 若含观察之外的数据，先作为错误观察回喂模型重答；
仍失败才使用确定性模板。

**理由**：答辩要证明的是 Agent 能规划、使用工具、从失败中恢复，而不是把
高频问题预先写死。数字正确性不交给模型口头承诺，仍由工具观察和确定性
检查保证。

## ADR-3 · 结构化数据 tool-use，非结构化 BM25 —— 而非全场景 RAG

**决策**：库存/欠款/采销等结构化问答走工具调用 + 数字接地；操作文档与历史
单据检索走纯标准库 BM25（中文 bigram 分词）。

**否决向量 RAG 的原因**：
1. 结构化数字经检索块转述会丢精度且不可审计，违背「答案可追溯到 ERP 真实值」
   的项目承诺；
2. embedding 依赖外部 API 或本地模型，与「纯标准库自建、可离线」承诺冲突；
3. 文档/历史语料小（百级块），BM25 的可解释命中（相关度分数）比语义检索
   的黑盒相关性更符合课程评审的可验证性要求。

**诚实记录**（C8）：BM25 的价值在文档/历史增长后体现；当前演示库收益小。

## ADR-4 · 写入闸门用 HMAC 无状态令牌 + 持久化 nonce 黑名单

**决策**：confirm_token = base64(payload).HMAC，payload 含草稿哈希/过期/nonce；
一次性由 `data/used_tokens.jsonl` 黑名单保证（TTL 窗口自动清理）。

**替代了**：内存 dict（原实现）——服务重启全部待确认令牌失效、多进程部署
（gunicorn 等）不可用。

**取舍**：meta（原话/模型等审计上下文）随令牌自描述，token 变长（数百字节）
但换来自描述与跨进程可验；黑名单每 commit 追加一行，量级可忽略。

## ADR-5 · 主动澄清用规则检测而非 LLM 自判

**决策**：澄清触发条件（无明细/无数量/无往来单位/无单价）由确定性规则产生，
不花 LLM；澄清问题文案也是模板。用户补充回答复用既有多轮修正链路
（prev_draft 随输入回喂）。

**理由**：澄清的判断条件是结构性的（字段有无），LLM 自判反而引入不确定；
一条链路两种用途（修正/澄清补充），架构上零新增状态机。

**上限**：2 轮，超限自动 skip_clarify 出确认卡——防止无限追问烦人。

## ADR-6 · token 预算是防失控保险丝，步数预算才是主约束

**决策**：`DEFAULT_MAX_TOKENS = 40000`（远大于单步消耗）。

**教训来源（C3）**：曾设 6000，在网关 custom 模式（每请求固定注入 ~8.5K
人格提示词）下第一次 decide 后即熔断，模型被迫「预算已用完」式收尾——表面
是模型偷懒，实际是自设预算与网关固定成本冲突。保险丝的阈值必须按
「最差环境（有固定注入的网关）」校准。

## ADR-7 · SSE 流式过程展示（action 事件先于工具执行）

**决策**：`/api/ask/stream` 事件序 start → action（决策出工具、执行前）→
step（trace 落定）→ done。action 事件让前端在工具执行时即显示
「正在查询库存…」，而不是等执行完才补历史。

**实现约束**：纯标准库 `http.server` 下以 `Connection: close` 界定响应结束；
前端 fetch + ReadableStream 解析（EventSource 不支持 POST）；流式不可用时
自动降级普通一次性接口（老 WebView 保底）。

## ADR-8 · 用量计量：能精确则精确，不能则估算并标注

**决策**：流式请求带 `stream_options.include_usage`（网关 400 一次后记忆
降级），非流式读响应 usage；都拿不到按字符估算（×0.8 系数）且
`estimated: true` 落盘。每次调用（含 agent 每步、洞察一跳）都记
`data/usage.jsonl`，分 purpose 聚合。

**理由**：token 效率叙事必须有真实台账支撑；估算值不标注会污染对比实验
（C3 的排查正依赖台账的精确值区分网关固定注入）。

## ADR-9 · 问答全库只读视野 + 决策/生成分模型

**背景**：工具箱只有库存/单据统计/检索 9 个窄工具，「有多少个供应商」这类
问题模型无工具可用，只能在无关工具里空转 4 步后超时答不上来；要覆盖
「整个 ERP」不能再靠枚举专用工具。

**决策**：新增 `core/dbread.py`——`docker exec` 调 erp-mysql 容器内的 mysql
CLI（零第三方依赖），`sql_query` 只读查全库；表结构从 `information_schema`
动态读取并缓存注入 context（不硬编码表清单），`db_schema` 按需给字段与枚举
取值采样。护栏：单条 SELECT 校验 + 只读事务（`START TRANSACTION READ ONLY`，
MySQL 层拒绝任何 DML）+ 语句超时 + 200 行/单元格截断。写入仍只走官方 REST
API；高频主数据计数仍由模型选择 `master_count` 工具一步完成（2026-11-20 统一循环后规则预路由退出决策位，ADR-2 修订）。

**教训（F10）**：推理模型在 agent loop 里会烧掉上万 token 做思考，单步
120~170 秒甚至返回空正文；给决策类调用封 `max_tokens` 后仍不稳定，最终把
问答决策切到低延迟模型（`llm.agent_model`，登录者显式配的私有档案优先），
`parse` / `insight` 等长文本生成仍用用户选的档案。表结构与主数据只在第 1
轮注入，后续轮靠 observation 继续，避免重复长上下文引发过度思考。


## ADR-10 · 问一问 supervisor 化：写意图路由到草稿，写入仍归闸门

**背景**：问一问只会读不会写——用户在对话里说「给永辉卖50瓶可乐」，得到的
回答是「只能查询，录单请用对话录单入口」，把同一句话在两个入口各打一遍。
写能力是 agent 化最自然的下一步，但直接给 agent 写权限会推翻 C1-C4 全部
安全设计（自主写库 = 无人确认事件）。

**决策**：问一问的 agent loop 升级为 supervisor——新增 `draft_order` 工具
（ask.py），把录单意图路由到「草稿预览 + 逐单确认令牌」：内部复用对话录单
的 `llm.parse → draft.resolve → gate.issue` 同一条管线（core/draft.py 的
`prepare_bills`，三入口共用一份实现）。写权限边界在工具层划死：

- agent 自主性到草稿为止——工具绝不调用 `draft.commit`，token 与草稿内容
  哈希绑定，写入必须由用户在前端确认卡上确认（`/api/commit` 校验令牌）；
- prompt 单层约束不可信：改库存/删单据类文本即使被模型误路由进 draft_order，
  也在工具层用正则拒绝（防「把库存改成999」被解析成一张出货 999 的单）；
- 草稿载荷只走 draft 事件给前端，不进模型观察（省 token，防复述大 JSON）；
- final 里的数字仍受数字接地校验约束——观察摘要里带金额/数量，答案可追溯。

**后果**：前端 /ask 升级为统一「智能助手」入口（查账 + 起草一个对话流），
确认/改数/逐单提交直接复用 multi-entry 的 `showMultiPreview` / `commitBatch`
（同一套 UI、同一个闸门、同一种审计形状）；/new 表单模式保留为兜底。
放弃的方案：给 agent 直接挂 create_bill 写工具（推翻人工确认不变量，否决）；
前端把录单文本转跳 /new（体验割裂，且丢失对话上下文）。

## ADR-11 · 录单校验 agent：草稿出预览前过一个只读取证 loop + 操作员习惯记忆

**背景**：录单解析是「一次抽取 + 规则清洗」，缺单价时只能出规则话术追问、
没说仓库只能落配置默认仓——模型明明能查「这个客户上次多少钱、这个人习惯用
哪个仓」，却没被组织进流程。多步化是自然的升级，但让 agent 改单据内容
会破坏「草稿哈希绑令牌」的闸门不变量。

**决策**：`core/billcheck.py`——parse 之后、签令牌之前插入一个 max_steps=3 的
只读取证 loop（复用 run_agent 引擎，`prompt_template` 参数换提示词）：

- 工具全只读：`stock_check`（库存够不够）/ `last_price`（该往来单位该商品
  最近真实成交价）/ `habit_defaults`（操作员习惯仓库与价格）/ `party_history`
  （往来单位近况与欠款）；
- 校验结论走 `submit_verdict` 工具的 args 通道而非 final——结论里的 confidence
  等自报数字不属于 ERP 观察，走 final 会被数字接地校验整体退回（不变量不开洞）；
- 模型只能「建议」patch，写回是确定性代码（`apply_patches`）：白名单字段
  （depot/price）+ 置信度 ≥0.85 + 只补缺失不覆盖 + 越界拒绝；
- patch 落定后的草稿才签令牌——令牌仍与最终草稿哈希绑定，闸门不变；
- 习惯记忆 `core/habits.py`：commit 成功后沉淀（jsonl 只增不改），读侧按
  操作员聚合（本人无记录退全局口径），价格习惯倒序取最近一笔；
- 追问升级：agent 生成的自然语言追问优先，规则追问兜底；多单仍不跨单追问
  （multi-entry 设计决策不推翻），追问内容降级为确认卡上的提醒条；
- 校验失败/未配模型降级 skipped——校验是增益不是闸门，解析结果照常交付。

**实测教训（B2）**：REST `getDetailList` 不吐真实行单价（unitPrice null，
只有商品档案价快照 purchaseDecimal），last_price 改走 dbread 只读 SQL 直查
`jsh_depot_item.unit_price`——护栏（SELECT 白名单 + 只读事务）原样生效。

**证据**：`eval/billcheck_cases.jsonl` v1（4 条，含无历史价宁缺勿错用例）+
`eval/run_billcheck.py`；2026-11-16 实测 4/4，SSE 取证步骤逐个可见，patch
理由引用观察（「成品仓电池库存 70 节足够本单 10 节」）。

## ADR-12 · 导入修复 agent 与老板日报 agent（有界自主的两个新工位）

**背景**：multi-entry 把 AI 限制在三个有界位置（抽取/认列/一次映射修复环），
「需处理」行全留给人工；洞察/日报（insight.py）纯规则零自主。Agent 化的
空位在「修复」与「综合判断」——都不该碰数字与闸门。

**导入修复（P-C，core/repair.py）**：确定性变换核心不动（可单测、可复现），
修复 agent 只对 problems 行做只读取证（find_material / find_party /
search_history 历史原话），结论走 submit_verdict args 通道；写回白名单只有
item_name / party，qty/price 永远是 agent 不可触碰字段（数字正确性归确定性
变换），material_id 需过 material_by_id 存在性校验（点选直达语义）；
confidence < 0.85 只进建议（前端「采纳」按钮），≥0.85 自动写回后仍要过
resolve 重签令牌。自动修复环限 ≤10 行（超出说明映射坏了，该改映射）。

**老板日报（P-D，core/daily.py）**：全项目唯一「无人触发」的 agent——当日
懒触发 + 缓存（commit 成功后 invalidate，数据变了昨天的结论不再可信）；
agent 自主决定最值得说的 3~5 个点（8 只读工具 + submit_verdict），每个点的
detail 数字逐点过 numeric_grounded（编造即丢点，宁缺勿滥）；补货建议
suggest_drafts 剥价格、party 必须出现在观察里，落确认卡走闸门；LLM 失败
降级规则模板（数字全真）。仅管理员可见（老板视角，_handle 层门禁）。
实测教训：MAX_STEPS=5 会被「想多看一眼」烧满被迫降级 → 7 步（配合 `submit_verdict` 终结型工具，结论提交后立即退出不再浪费额外一轮 final）。

## ADR-13 · P4 规模欠款漏报的修复：三路尝试的完整证据链与 SQL 聚合终案

**问题（P4 open item）**：单类单据 >200 张时欠款合计漏老账（260 张真欠款实测
漏 23%）。REST `/depotHead/list` 的规模行为是根因，两条修复路线先后被实测否决，
最终落在「聚合数字直查 DB」。

**尝试一（2026-11-09，已回滚）**：时间窗二分 sweep——未收敛。本次重查根因：
`beginTime/endTime` 过滤器语义不稳定——压测态实测宽窗 [2000, 今天] 返回全量、
窄窗（无论按 oper_time 还是 create_time 划）返回 0 行，与两个字段都对不上，
按任何时间轴二分都无法收敛（本次以 30 窗口/0 截断的全量轨迹复证）。

**尝试二（本次，已废弃）**：`sweep_time_buckets` 纯函数递归塌缩（区间按天减半
保证终止 + 单日溢出诚实截断标记）。单测 5 例全绿，但在真 REST 上失效——
同一个窗口查询两次调用分别返回 200/400 行（自适应翻页 page2 间歇失效/整页
重复，list() 层 29aaf8d 的 currentPage/pageNo 重试也压不住），时间桶的前提
「同窗口结果确定」不成立。连同 `bills_window` 问一问工具一起废弃——宁可
不提供工具，不提供会在规模下悄悄给错数的工具。

**终案（core/report.py `_debt_sql`）**：欠款合计与 top 归因直查 DB（dbread
只读通道，ADR-9 同一条护栏链：SELECT 白名单 + 只读事务 + 截断）。口径：
欠款 = 表头 `total_price − change_amount`（与 stress_scale 真路径 ground
truth 同一公式），仅审计单计入，tenant 以登录用户子查询锚定。REST 路径
（all_bills 逐单 debt 累加）保留为 dbread 不可达时的降级——宁可老口径也不
空手。验收：压测态 `debt_pay_total = 15600.0` 与 gold 分毫不差（漏报 0），
top 归因正确；`summary`/看板/问一问 debts 工具同一数据源全部受益。

**方法论沉淀**：P4 两次「修复失败」都不是白做——每次都把根因边界往前推了一格
（11-09 证明翻页不可靠 → 本次证明时间过滤不可靠 + 翻页间歇失效会传染自适应
重试），最终把问题归类到「聚合 vs 明细」的架构分界：明细清单走 REST（分页
瑕疵可容忍、行级展示），聚合数字走 SQL（分毫不差、可被 stress 探针直验）。

## ADR-14 · 统一主入口与会话内草稿修正（2026-11-20）

**背景**：早期版本把「问一问」「对话录单」「图片导入」「Excel 导入」拆成多个入口；
问答主流程还保留规则直答抢跑。评审反馈功能完整但 Agent 化不足：录单像一次抽取，
问答像规则分发。

**决策**：
1. `/ask` 成为唯一主入口，桌面与移动端使用同一对话；
2. 所有自然语言请求都进入统一循环：意图理解 → 工具调用 → 观察 → 修正 → 答案或草稿；
3. 草稿是显式会话状态，允许「改成60瓶」「还是那家」式修正，但不保存可重放令牌；
4. 图片与 Excel/CSV 都进入同一草稿确认卡；表格列映射与修复保留专项 Agent；
5. 写入仍使用一次性令牌、内容哈希、审计与逐单确认。

**取舍**：不再以“0 token 规则直答”为主卖点。确定性统计仍是工具，何时调用由
模型决定；当模型选择错误时，工具错误和接地检查会把它拉回，而不是提前用规则
替代思考。

**证据**：
- `tests/` 200 项离线测试全绿；
- `eval/run_unified.py` 5/5（查询、统计、起草、澄清、危险请求）；
- 浏览器端到端：桌面与 390px 无横向溢出，草稿卡 → 确认层 → 写入状态闭环；
- 接口级写入 `00000000749` 后库存 0→1，随后通过 seed 恢复演示基线。

## ADR-15 · 补货数量交给确定性算法，诊断结论绑定调查链（2026-11-23）

**背景**：新增两项能力——智能采购建议（看板卡片 + 对话工具）与 AI 经营诊断
（多步调查）。两者都有同一个退化风险：把数字交给 LLM 猜、把看板数据复述一遍
当结论。

**决策**：
1. **补货量是纯函数**：日均净销量 ×（采购间隔中位数 + 覆盖天数）+ 安全库存 −
   （当前库存 + 在途未审采购量 `pending_qty`），向上取整（commit `77a9c36` 补齐在途扣减，避免重复下单）。LLM 只决定「建议哪些商品」，日报与采购草稿的数量一律取
   算法值；接口 `/api/procurement/draft` 只收商品 id 列表、**不收数量**，防草稿
   脱离可复算口径。
2. **安全库存口径修正**：预警阈值从 `material/list` 的 `lowDecimal`（schema 语义
   是「最低售价」，价格字段）改为 `jsh_material_initial_stock.low_safe_stock`
   （数量，material_id × 仓库，跨仓求和）；SQL 不可达降级为全局阈值。
3. **诊断结论绑定调查链**：每条 issue 必须声明 `evidence_steps`（工具步骤序号），
   证据数字只能来自这些步骤的观察（比全观察池更窄）；索引无效退全池并标 `lax`；
   全部被丢降级 `insight.insights()` 规则模板。
4. 零销量商品不催货（负库存提示盘点）；无历史供应商的商品不进草稿（不猜）。

**后果**：采购建议可在任何环境用同一公式复算；诊断与日报的差异有了结构证据
（模型必须真的下钻）；SQL/LLM 任一不可用时显式降级，不空转、不猜数。

**证据**：
- `tests/test_procurement.py` 8 项 + `tests/test_diagnosis.py` 5 项；全量
  `python3 -m unittest discover -s tests` 198 项全绿；
- 本地冒烟：`GET /api/procurement/suggest`、`POST /api/procurement/draft`、
  `POST /api/diagnose`、`POST /api/diagnose/stream` 路由均通，无 ERP/模型时返回
  中文降级提示；
- 设计口径全文见 `docs/智能采购与深度诊断设计.md`。

## ADR-16 · 事实与建议分离、终结型工具与智能快路径（2026-11-25）

**背景**：升级统一 Agent 与录单校验循环后，2026-11-24 完整链路评测暴露出两个退化：
1. **录单整单准确率从旧单跳 96.7%–98.3% 跌至 88.7%–91.5%**：根因是两股错误叠加——
   (a) `billcheck.apply_patches` 把历史价/习惯仓**静默写回**原草稿（覆盖用户原话未提的 `price=0` 和 `depot=""`），一旦操作员习惯文件积累历史记录就会系统性篡改未提仓库/单价的草稿；同时补丁缺少观察接地校验与单位一致性校验（易将「瓶」价错套到「箱」单）。
   (b) `SYSTEM_PROMPT v7` 存在 4 处真实抽取泄漏：编号商品名（如「商品17」）被拆成单价 17、模糊量词（「一批」「拿点」）被猜成 qty=1、省略往来单位时从 few-shot 示例串台复制「美宜佳」或单价 3.5。
2. **录单延迟飙升（parse 3.6s → 11.19s，/ask 起草 33.71s）**：
   (a) 即使单据 7 项核心要素全部齐全、高置信度，校验 Agent 仍无条件跑 2~3 轮 LLM 循环；
   (b) `submit_verdict` / `submit_diagnosis` 提交结论后 `run_agent` 仍多跑一轮无意义的 `final` 文本生成（或触发预算耗尽 `forced_final`）。

**决策**：
1. **事实与建议分离（Separation of Facts & Grounded Suggestions）**：
   - 抽取草稿（`drafts[]`）**永远忠实还原用户原话**，绝不静默覆写 `price` / `depot`；
   - `billcheck.apply_patches(..., observations=real_obs, apply_to_draft=False)` 强制对每个建议补丁做**观察接地校验**（建议价格必须出现在非 `submit_verdict` 工具观察的数字集合中，建议仓库必须出现在工具观察文本中）与**单位一致性校验**（`_tool_last_price` 优先精确 `material_id` 匹配并比对单位，不一致时标 `unit_mismatch` 拦截）；
   - 通过校验的高置信补丁存入 `check.patches_suggested`，在前端确认卡（`/ask` 与 `/new`）渲染为带证据理由的**一键采纳 chip**，点击后再写回草稿并触发重新预览重签令牌；追问文案也自然融入查到的参考价。
2. **终结型工具（`terminal: True`）**：`run_agent` 支持终结型工具标记；`billcheck` / `daily` / `repair` 的 `submit_verdict` 与 `diagnosis` 的 `submit_diagnosis` 执行成功后立即收尾退出，每轮立省 1 次无效 LLM 往返，杜绝多余 `forced_final`。
3. **确定性快路径 + 完整 Agent 慢路径**：要素齐全且高置信度的单据在 `billcheck` 内直接走确定性 `stock_check` + `habit_defaults` 预检（0 额外 LLM 调用，仍保留真实库存风险与步骤轨迹）；凡缺字段/缺单价/低置信/有解析问题，立即进入完整 `max_steps=4` 多步校验 Agent 循环。
4. **提示词升级 `v8-20261125` 与复合问句显式拆解接入**：堵死示例串台、编号拆价、模糊量词猜 1 三个漏洞；将已写好但未接入的 `ask._compound_hints()` 修复「还有多少」误拆后正式接入主循环，同时把 `master_count` 注册进 `ask._tools()`。

**实测证据（2026-11-25，OpenRouter `deepseek/deepseek-v4.1-flash-1017`，本地种子库）**：
- **71 条录单完整链路**（`eval/run.py --full-chain --tag v8-stabilized-20261125`）：**71/71 = 100.0%** 整单全对、**0 幻觉**、**0 报错**，均值延迟 **11.19s → 4.92s（提速 56%）**，p95 **19.07s → 16.19s**；
- **校验 Agent 专项**（`eval/run_billcheck.py`）：**4/4 = 100.0%**（b1–b3 均产出接地参考价建议，b4 无历史价严守宁缺勿错）；
- **34 条问答全量**（`eval/run_ask.py`）：**33/34 = 97.1%**（`agent` 100%、`compound` **67% → 100%**、`boundary` 100%，均值延迟 **5.39s** / p95 **9.22s**）；
- **统一 Agent 冒烟**（`eval/run_unified.py`）：**5/5**，其中起草延迟 **33.71s → 10.24s（提速 70%）**，澄清延迟 **29.05s → 11.81s（提速 59%）**；
- **离线回归测试**：25 个模块 **236/236 全绿**（新增 17 项回归测试覆盖终结工具、观察接地、单位一致性、并发 nonce 原子防重放、分档案 `_quirks` 隔离、64KB 历史分块与服务端修复项）。
