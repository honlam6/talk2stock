# 基线对比实验手册（原生 jshERP vs Talk2Stock）

> 目的：用可复现的实验回答「Talk2Stock 到底省了多少事、省在哪」。
> 最重要的认知：**你们是 ERP 门外汉不是缺陷，是实验条件**——目标用户（小商贸公司内勤）
> 同样没受过 ERP 训练。三组没经验的人测出来的数字，比一组熟练用户更有说服力。
> 本手册写好后，实验半天可以做完。

---

## 一、实验设计（为什么是两个场景，而不是一个）

提案的核心洞察是：ERP 痛的不是"录单"，而是两段时间——**翻译成本**（话 → 字段）
和**档案修复成本**（缺档案要先停下去建档）。所以基线必须把这两段拆开测：

| 场景 | 档案状态 | 测的是什么 | 预期结论 |
|---|---|---|---|
| **A · 档案齐全** | 供应商/商品提前建好 | 纯翻译成本：同样的信息，两种界面各要多久 | 原版不算灾难（点几下），Talk2Stock 仍快数倍 |
| **B · 档案缺失** | 语料含新供应商/新商品 | 档案修复成本：原版要中断去建档，Talk2Stock 确认时自动建 | 原版耗时/中断次数暴涨，差距拉开 |

**场景 A 的意义是"归因"，不是"证明原版好用"。** A、B 两场景的差值 =
档案修复成本；A 场景里 Talk2Stock 的优势 = 翻译成本。有了这组拆分，
报告才能回答「你的加速到底从哪来」，也直接回应提案第二节"档案配齐时录单并不慢"的查证。
（这就是消融实验 ablation 的思路：每个部件的贡献分开算。）

## 二、材料

1. **任务卡 20 张**：每张一张纸条/卡片，写一条业务信息（和 `eval/cases.jsonl` 的
   n01–n20 同源，保证基线与 AI 评测用同一批业务）。示例：
   > 「美宜佳送来 30 瓶可乐，3 块 5 一瓶，放原料仓」（场景 A：档案已有）
   > 「日化批发部送来 100 块肥皂，一块 4 块 5」（场景 B：供应商、商品都要新建）
2. **两台电脑/浏览器窗口**：一台开原版 `localhost:8080`，一台开 Talk2Stock `localhost:8090/ai`。
3. **计时**：手机秒表即可；主试负责掐表，被试只管操作。
4. **记录表**：`eval/baseline_timing.csv`（见 §五）。
5. **录屏**（强烈建议）：QuickTime 录原版操作——第一次上手的手忙脚乱就是
   报告和展示会里最有说服力的 30 秒。

### 被试与分工
- 3 名组员（LuKexin / YangYawen / HuangZihao 或任意三人），都按"第一次用 ERP"的身份操作。
- 每人每个场景录 20 条中的 6–7 条，交叉分配，避免顺序效应。
- 主试 1 人掐表记录（可由第 4 名组员或轮流担任）。

## 三、操作脚本

### 场景准备
- **两个场景的共同起点**：`python3 eval/seed_demo.py --yes` 一键把数据库重置成受控演示状态
  （固定的往来单位/商品/9 张单，日期相对今天分布，无负库存）。谁弄乱了库，重跑一遍即还原。
- **场景 A**：用管理员账号把 20 条任务卡里涉及到的供应商/商品全部在
  「基础资料」里建好（这一步是实验处理的一部分，不算入被试时间）。
- **场景 B**：确认任务卡里的供应商/商品都不在档案里。
- Talk2Stock 侧：同一批任务，场景 A/B 不需要准备（这正是要测的）。

### 原版 jshERP 操作步骤（贴在被试手边）
1. 打开 `http://localhost:8080`，登录（账号由主试提供）
2. 侧边栏 → 采购管理 → 采购入库 → 新增
3. 选供应商（下拉找；找不到 → 去 基础资料→商家信息→新增→保存→回来重选）
4. 明细行：选商品（弹窗搜索；找不到 → 基础资料→商品→新增→回来重选）
5. 填数量、单价
6. 检查单据日期、编号、结算账户、本次付款
7. 保存 → 审核

### Talk2Stock 操作步骤
1. 打开 `http://localhost:8090/ai`
2. 把任务卡上的信息**组织成一句话**打进去（允许看卡组织语言，计入时间）
3. 看确认卡：核对待新建清单、单价为 0 警告、匹配提示
4. 点「确认写入 ERP」→ 看到绿色成功提示

### 流程规则
- 开始前允许 2 分钟自由熟悉界面（不计入正式数据，避免纯慌乱噪声）。
- 每条从"主试说开始"到"单据保存/写入成功"计时。
- 记录三类事件：**总耗时**、**操作错误**（点错、填错后返工）、**中断**（原版去建档来回）。
- 卡死超过 3 分钟判失败，记 180s 并标注。
- 完成后当场把数字填进 CSV，不要凭记忆补。

## 五、记录表

`eval/baseline_timing.csv`（本仓库已附模板），列定义：

| 列 | 含义 |
|---|---|
| subject | 被试编号 S1/S2/S3 |
| scenario | A=档案齐全 / B=档案缺失 |
| tool | erp=原版 / t2s=Talk2Stock |
| task_id | 任务卡编号（n01…n20） |
| seconds | 总耗时（秒），失败记 180 |
| errors | 操作错误次数（点错、返工） |
| interrupts | 中断建档次数（仅原版会出现） |
| notes | 备注（卡在哪、点了什么） |

## 六、怎么用结果（写进报告的三张表/图）

1. **耗时对比表**：场景 A、B × 原版、Talk2Stock 的均值/中位数（每人分开列）。
2. **中断次数**：场景 B 里原版的中断次数 × 平均中断耗时 → "档案修复成本"的实测值。
3. **失败率**：多少条卡死/放弃 → 配合录屏截图放进 failure analysis。

报告里必须写清口径：被试是无 ERP 经验的学生（= 目标用户画像）、每格几个人几条、
有没有剔除熟悉练习。**数字不漂亮也比口径含糊强**——课程评分明确要求
"success criteria defined before testing"（本手册就是"before testing"的证明，先交手册再跑实验）。

## 七、中期精简执行版（1.5 小时，24 个计时点）

> 中期只要"早期结果 + 方向判断"，不需要统计功效。上面的全量设计留给终期；
> 中期按本节跑，数据量从约 78 点降到 24 点，结论口径不变。

### 7.1 规模

3 名被试 × 4 条任务 × 2 种工具 = **24 个计时点**，每格 n=3。每人 8 次操作，
单次 1–3 分钟，含准备约 1.5 小时。

### 7.2 任务卡（与 `eval/cases.jsonl` 同源）

| 场景 | task_id | 任务内容 | 档案状态 |
|---|---|---|---|
| A 档案齐全 | n01 | 向美宜佳采购可乐 30 瓶，单价 3 块 5，入原料仓 | 供应商、商品都已有 |
| A 档案齐全 | n03 | 从农夫山泉进矿泉水 100 瓶，单价 2 元 | 都已有 |
| B 档案缺失 | n22 | 老张那里进了 2 箱苹果，一箱 90 | 供应商、商品都缺 |
| B 档案缺失 | n23 | 买 10 台打印机，一台 1500，从京东企业购 | 都缺 |

**关键简化**：`seed_demo.py` 的固定数据天然同时满足两个场景——n01/n03 的档案在，
n22/n23 的不在，**不需要分别准备 A/B 两套数据库**。

四个任务全是**采购入库**，业务类型一致，且不依赖期初库存（销售出库在 seed 数据里
可能库存为 0，会因「库存不足」失败，不能用来测录入速度）。

**重置规则**：每位被试开始前跑一次 `python3 eval/seed_demo.py --yes`。
否则上一位在 B 场景新建的「老张/苹果/打印机」会让下一位的 B 场景失效。

### 7.3 执行顺序（抵消学习效应）

| 被试 | 顺序 |
|---|---|
| S1 | A-erp → A-t2s → B-erp → B-t2s |
| S2 | A-t2s → A-erp → B-t2s → B-erp |
| S3 | A-erp → B-erp → A-t2s → B-t2s |

记录表用 `eval/baseline_timing_slim.csv`（24 行，已按 S1–S3 排好）。

### 7.4 报告只放一张表

| 场景 | 工具 | n | 中位耗时 | 均值 | 错误合计 | 中断合计 |
|---|---|---|---|---|---|---|
| A | 原版 | 3 | | | | |
| A | Talk2Stock | 3 | | | | |
| B | 原版 | 3 | | | | |
| B | Talk2Stock | 3 | | | | |

加一句 limitation 即可：「pilot 阶段，每格 n=3，只用于方向判断；终期扩到 20 条 × 3 人」。

**不做**：显著性检验、异常值剔除（在 notes 里写原因）、A/B 两套独立环境准备。
卡死超过 3 分钟记 180s 并标注。

### 7.5 三个人同时跑（同一套业务结构，档案名做逻辑隔离）

这台机器内存 1.8GB、已用 1.6GB，起第二套 ERP 不现实；T2S 的 ERP 连接和数据目录
也都是全局的。要并发只能用「任务结构相同 + 档案名后缀」做逻辑隔离：

| 被试 | A 场景（共享档案） | B 场景（各自缺失，互不污染） |
|---|---|---|
| S1 | n01、n03 | 老张S1 / 苹果S1；京东企业购S1 / 打印机S1 |
| S2 | n01、n03 | 老张S2 / 苹果S2；京东企业购S2 / 打印机S2 |
| S3 | n01、n03 | 老张S3 / 苹果S3；京东企业购S3 / 打印机S3 |

- A 场景档案共享，并发录入只会累加单据和库存；采购入库不校验库存，不会失败。
- B 场景只是把供应商/商品名加被试后缀，字段数、业务类型、话术结构完全一致，
  三个人各建各的档案，互不把对方的「缺失」变成「已有」。
- 报告里写一句：「B 场景档案名加被试后缀以避免并发污染，任务结构一致」。
- T2S 的 `audit.jsonl` / `usage.jsonl` 是共享文件，按 `operator` / `user` 字段过滤到个人。
- 三个人同时调用 LLM 时每条任务错开 30–60 秒，网关限流会把延迟算进计时。
- 如果要求连档案名都完全一样，就不能并发：每人开始前 `seed_demo.py --yes`，串行跑。
