# 导入智能体：任意 Excel 进来以后，系统自己走完哪几步

> 目标：用户丢一个**任何来源**的表格（金蝶导出、用友导出、手工流水、别人微信发的表），
> 系统自己看懂结构、自己拿主意、拿不准就问一句、能自己修的自己修，最后给出可导入的草稿。
> 关键不是「让 AI 猜」，而是**让每一步都有依据、可回放、可人工接手**。

## 0. 为什么不能一步到位

真实表格的坑不在「列名叫什么」，而在这些地方：

| 现实情况 | 一步到位的 AI 映射会怎样 |
|---|---|
| 第 1 行是「XX公司送货单」标题，表头在第 2/3 行 | 把标题当表头，整表错位 |
| 一个文件 3 个 sheet（明细/汇总/说明） | 猜错 sheet，导出一堆空行 |
| 「数量」和「件数」两列都在 | 静默挑一个，单位全错 |
| 表尾有「合计」行 | 合计数被当成一张单 |
| 日期是 `05/01/2024`（日月顺序不明） | 整列解析失败或日期全错一个月 |
| 没有往来单位列（整张表都是同一个客户） | 每行都缺必填字段，全表失败 |
| 多行共用一个单号 | 每行建一张单，单据数翻倍 |

所以流程必须是：**先看结构 → 再拿主意 → 拿不准问人 → 能修的自修 → 复核**。

## 1. 五步流程

```
上传文件
  │
  ├─① 看（profile，纯规则，0 token）
  │    表头候选打分（词典命中 + 文本占比 + 下一行是否数字）
  │    数据区起止（合计/小计行识别）
  │    每列类型画像（数字/日期/文本占比、样本、去重数）
  │
  ├─② 定（plan，纯规则）
  │    列 → 字段（词典 + 类型一致性打分，一列只归一个字段）
  │    per_row / group（有单号且重复率高 → 按单号合并）
  │    整表业务类型（表头字眼 / 有「入库·出库」取值列）
  │    → 先产出一版「我认为对的映射」
  │
  ├─③ 问（questions）
  │    只问真正拿不准、且答案会改变结果的（≤4 个，必答优先）
  │    用户答完 → 带 answers 重算（≤2 轮，不答按默认值走）
  │
  ├─④ 修（auto_repair，纯规则，0 token）
  │    日期整列解析失败 → 自己试 8 种格式，取救回最多行的那种
  │    试错过程写进 trace（「试了 8 种，采用 %d/%m/%Y，错误 2 → 0」）
  │
  └─⑤ 复核（transform 试跑）
       逐行出草稿 + 问题；失败行占比 ≥40% 时再问一句「先跳过这批行？」
       → 通过后进入既有的「预览 → 逐单令牌 → 批量写入」
```

## 2. 谁做的决定：四种来源，全部可查

| 来源 | 含义 | 例子 |
|---|---|---|
| `rule` | 规则算的 | 「E 列叫数量、样本全是数字 → 数量列」 |
| `llm` | 模型补的（只在规则缺必需列时叫一次，且**不能推翻规则**） | 「叫『货品描述』的那列其实是商品名」 |
| `auto` | 自己试出来的 | 「日期试了 8 种格式，用日月顺序救回全部行」 |
| `user` | 你答的 | 「用 B 列当数量」 |

每一步都写进响应里的 `trace`：

```json
{"step": "auto_repair", "action": "自动修复日期格式",
 "detail": "试了 8 种格式，采用 %d/%m/%Y（日期错误 2 → 0）",
 "source": "auto", "confidence": "high"}
```

前端把 trace 渲染成「决策过程 N 步」，点开能看到每一步的依据——答辩时可以直接指着它讲，
而不是说「模型比较聪明」。

## 3. 会问哪些问题（结构化，不是自由聊天）

| id | 什么时候问 | 形态 |
|---|---|---|
| `sheet` | 文件里有多个非空工作表 | 选择（表名 + 行列数） |
| `header_row` | 前几行都像表头、得分接近 | 选择（带每行原文预览） |
| `field:item_name` / `field:qty` | 缺必需列 | 选择（所有列 + 样本） |
| `field:party` | 没有往来单位列 | 选择列，**或直接填「整表都是这个客户」** |
| `field:qty`（多候选） | 「数量」「件数」两列都在 | 选择（两列样本对照） |
| `col:C:field` | 一列能当两个字段，得分几乎一样 | 选择（A 字段 / B 字段 / 忽略） |
| `mode` | 单号列重复率 ≥50% | 选择（合并成一张 / 每行一张） |
| `biz` | 表头有出入库字样但看不出方向 | 选择（采购/销售/退货） |
| `skip_failed` | 失败行 ≥40% | 布尔（跳过先导 / 回去改映射） |

规则：**最多 4 个、最多 2 轮**；必答的排前面；这一轮答过的不重复问；不答按默认值走并留痕。

## 4. 不变量（这块坏了整个导入就不可信）

1. **计划层不写库、不签令牌**：`import_agent.py` 里没有任何 ERP 调用或 `gate.issue`，
   只产出映射、草稿和问题。写库仍是原来的「预览 → 确认卡 → 逐单令牌 → commit」。
2. **没有模型也能跑**：规则层覆盖常见表头；模型只是补位。`llm_fn=None` 时全流程正常。
3. **模型不推翻规则**：模型只在规则缺必需列时补认，冲突变成问题交给用户。
4. **所有用户答复都留痕**：`source: user` 的 trace 会进审计链路（谁把「件数」改成了数量）。
5. **有界**：问题 ≤4/轮、轮次 ≤2、自修最多 8 次尝试、行数 ≤500。

## 5. 接口

| 接口 | 入参 | 出参 |
|---|---|---|
| `POST /api/sheet/inspect` | multipart 文件 | `ref` + 工作表清单 + 前 8 行预览 |
| `POST /api/sheet/plan` | `{ref, sheet?, answers?, round?}` | `mapping` + `questions` + `trace` + `result` |
| `POST /api/sheet/answer` | 同上（`answers` 为 `{问题id: 值}`） | 同上（重算后） |
| `POST /api/sheet/transform` | `{ref, sheet, mapping}` | 人工改完映射后的确定性重变换（0 token） |
| `POST /api/sheet/resolve` | `{drafts:[{row_no, draft}]}` | 逐单预览 + 每单独立令牌 |

`/api/sheet/map` 保留为 `/api/sheet/plan` 的别名（旧前端不受影响）。

## 6. 演示脚本（两分钟）

1. 传一个表头在第 2 行、带「合计」行、有单号重复的送货单 → 系统说「有 2 处需要你确认」。
2. 点开「决策过程」：能看到它认了几列、为什么按单号合并、合计行为什么被跳过。
3. 答「数量用 B 列」→ 重算，问题清零，3 行合并成 1 张单。
4. 再传一个日期写成 `05/01/2024` 的表 → 它自己试 8 种格式，trace 里出现「自动修复」。
5. 传一个没有往来单位的表 → 它问「哪一列是往来单位 / 或者整表都是哪个客户」，填名字后全部补齐。
