# 智能采购建议 与 AI 经营诊断 · 设计说明

> 2026-11-23。两个功能共用同一套既有底座（agent 循环 / 只读工具面 / 草稿闸门），
> 不新建数据层、不新建页面体系。本文记录取舍判断、数据口径、算法与验收方式。

---

## 一、定位与取舍

两个需求不是平级新增，它们分别落在已有三条腿上：

| 已有资产 | 位置 | 本批用法 |
|---|---|---|
| 手写 agent 循环（JSON 动作 + 观察回喂 + 接地校验 + 预算） | `app/core/agent.py` | 深度诊断直接复用 |
| 只读取证工具面（库存/单据/欠款/全库 SQL） | `app/core/ask.py` + `app/core/dbread.py` | 诊断工具箱、对话入口的采购工具 |
| 草稿 + 逐单令牌 + 人工确认闸门 | `app/core/draft.py` + `gate.py` | 采购建议出草稿（`purchase_in` 现成） |
| 专用 agent 范例（换提示词 + 换工具箱） | `app/core/daily.py` | 诊断的结构模板 |

**取舍结论：采购建议是主交付，诊断是复用型副交付。**

- 采购建议的输出是数字，可用公式复算、可用 SQL 复核，可验收性强；且直接产出
  可确认的采购入库单草稿，完成一次业务动作。
- 诊断（多步调查）与日报高度重叠；为了不重复建设，给诊断加了日报没有的结构
  约束：**每条结论必须声明证据步骤（evidence_steps），证据数字只能来自那些
  步骤的观察**——强迫它真的下钻（销售额降了 → 追到哪个客户/商品/哪天掉的），
  而不是把看板复述一遍。

## 二、智能采购建议（`app/core/procurement.py`）

### 数据口径（全部只读，经 dbread 只读事务）

| 数据 | 来源 | 说明 |
|---|---|---|
| 当前库存 | `jsh_material_current_stock.current_number` | 分仓，ERP 审核单据后维护；跨仓求和 |
| 近期净销量 | `jsh_depot_item × jsh_depot_head` | 出库·销售 − 入库·销售退货，按商品汇总，窗口默认 30 天 |
| 采购历史 | 同上：入库·采购（近 180 天） | 最近采购价、最近供应商、采购间隔（相邻采购日期差） |
| 安全库存 | `jsh_material_initial_stock.low_safe_stock` | 每商品×仓库的最低库存数量，跨仓求和 |
| 商品主数据 | REST `/material/list`（`erp.materials()`） | 名称/型号/单位，带缓存 |

### 算法（写死在代码里，可复算）

```
日均销量 d = 窗口内净销量 / 窗口天数
采购周期 L = 该商品历史采购间隔中位数（样本 ≥2）
            否则用配置默认值（默认 7 天，结果里标注 assumed）
安全库存 S = low_safe_stock 跨仓合计（未设 = 0，标注）
目标库存 T = d × (L + 覆盖天数) + S          （覆盖天数默认 30）
建议量   = ⌈max(0, T − 当前库存)⌉
```

分级：库存为负 / 低于安全线 / 撑不到采购周期 → `urgent`；建议量 > 0 → `reorder`；
其余 `ok`。**护栏：日均销量为 0 的商品不催货**——负库存改提示「账实不符，建议盘点」，
避免把账务问题当采购需求。

配置（`config.json` 的 `procurement` 段，均有默认值）：

```json
{"days": 30, "cover_days": 30, "lead_time_days": 7}
```

### 接口与前端

| 端点 | 说明 |
|---|---|
| `GET /api/procurement/suggest` | 只读计算，零 LLM；30s 缓存，前端表格直读 |
| `POST /api/procurement/draft` | `{only:[material_id...]}` → 采购入库单草稿（逐单令牌，不写库） |

- 看板（`/dashboard`）新增「智能采购建议」卡：商品/当前库存/近 30 天销量/
  建议采购量/状态/理由 + 「生成采购草稿」按钮（复用确认卡 `showMultiPreview`）。
- 对话（`/ask`）注册 `procurement_suggest` 工具：说「该补什么货」直接出表格，
  建议量是观察值，final 可以引用（`agent.py` 规则 2 已加例外说明）。
- 数量只信服务端：`/api/procurement/draft` 只接受商品 id 列表，**不接受客户端
  传数量**，避免草稿脱离可复算口径。

### 草稿规则

- 按商品「最近采购供应商」分组，一张草稿一个供应商；
- 无历史供应商的商品进 `skipped`（不猜供应商，由用户在确认卡手选）；
- 价格用最近采购价（没有则 0，确认卡会亮「单价为 0」提示）；
- 写入仍走 `/api/commit` + 令牌闸门，本模块绝不直接写库。

### 安全库存与库存预警口径修正

旧实现 `stock_overview` 把 `material/list` 行的 `lowDecimal` 当预警阈值——该字段
在 schema 里是 `jsh_material_extend.low_decimal`，业务含义是**最低售价**（价格）。
本批修正：阈值改为 `jsh_material_initial_stock.low_safe_stock`（数量，material_id
维度，跨仓求和），无配置时退回全局阈值（默认 10）。SQL 不可达时降级为空映射，
预警退回全局阈值，不阻塞看板。

### 日报联动

`daily.py` 的补货建议（`suggest_drafts`）改为：模型只决定「建议哪些商品」，
**数量一律取 procurement 的算法值**；算法不认为要补的商品直接丢弃；供应商取
算法给出的最近采购供应商。SQL 不可达时日报不给补货建议（宁缺不错）。

## 三、AI 经营诊断（`app/core/diagnosis.py`）

### 结构

复用 `run_agent`（`max_steps=8`）：概览四件（今日/本月/库存/欠款）→ 模型挑 1~3 个
问题下钻（`query_bills` / `sql_query`）→ `submit_diagnosis` 收口。

提交结构：

```json
{"overview":"一到两句（引用观察数字）",
 "issues":[{"title":"12字以内","evidence":"引用观察里的数字","evidence_steps":[1,3],
            "cause":"可能原因","action":"改进建议","severity":"warn|info|good"}]}
```

### 校验（逐条，宁缺勿错）

1. 字段齐全、最多 3 条、severity 白名单归一；
2. `evidence_steps` 必须指向真实成功的工具步骤；有效时**证据数字只能来自那些
   步骤的观察**（比全观察池更窄）；索引无效 → 退回全观察池并标 `lax`；
3. `title + cause + action` 里出现观察外数字同样丢弃（防「日均亏损 3000」式编造）；
4. 全部被丢 → 降级到 `insight.insights()` 的规则模板（`degraded=True`，
   `source=rule_fallback`）。

### 接口与前端

| 端点 | 说明 |
|---|---|
| `POST /api/diagnose` | 同步版（工具/测试用） |
| `POST /api/diagnose/stream` | SSE：`action`/`step` 逐推（调查过程可见），`done` 带完整结论 |

- 仅管理员（与老板日报同一门禁）。
- 看板「AI 经营洞察」卡新增「深度诊断」按钮：结果卡四段式（数据证据/可能原因/
  改进建议/调查步骤），附可展开的调查轨迹。

## 四、视觉规范对齐（shell 侧栏时代的现有 UI）

- **外壳**：诊断结果卡与日报卡同款（1.5px 金色描边 + `#fffdf6` + 20px `--f-display`
  标题）；采购卡复用 `.card` / `h2 .bar` / `.btn-sm` / `.dtable` / `.tbl-wrap`。
- **语义色一律走 token**：紧急 `--rust / --rust-bg`、需补货 `--gold / --gold-bg`、
  充足 `--jade / --jade-bg`——首版硬编码色值已清除。
- **窄屏**：≤640px 表格整体隐藏，改用 `.proc-card` 卡片列表（与「最近单据」
  `.db-recent-cards` / `.bill-card` 同一模式）；标题行按钮换行沿用既有
  `.card > h2 { flex-wrap: wrap }` 规则。
- **对话主入口**：`/ask` 建议 chips 增加「补货建议」（与其余 chips 同款，
  窄屏为横向滚动条），保证新能力在唯一主入口可见。
- **验证**：桌面与 390px 截图（合成数据 route mock）、两页 `node --check`、
  浏览器控制台零错误。

## 五、共同不变量

1. **只读到底**：两个功能都不写库；采购草稿是唯一「可写入路径」，且仍须令牌+人工确认。
2. **数字可追溯**：采购量由纯函数算出；诊断证据逐条接地；LLM 从不自由生数。
3. **失败有兜底**：采购建议 SQL 不可达 → 明确提示；诊断 LLM 失败 → 规则洞察；
   日报补货建议算法不可用 → 空数组。
4. **不新建页面/数据层**：看板加卡、对话加工具，入口收敛策略不变。

## 六、验收

离线单测（`python3 -m unittest tests.test_procurement tests.test_diagnosis -v`）：

- 采购：公式与分级边界（含零销量、负库存、无安全库存、无采购周期）、SQL 失败降级、
  按供应商分组与 skipped、only 过滤、工具观察形状；
- 诊断：调查链接地（evidence_steps 指向 sql_query 下钻）、编造数字丢弃并降级、
  无效步骤退化全池并标 lax、未配置模型、LLM 全炸降级。

真库验证步骤（有 ERP 环境时）：

1. `GET /api/procurement/suggest` → 手写 SQL 复核 3 个商品的 `sold`/`stock`/
   `suggest_qty`（公式见上）；
2. 点「生成采购草稿」→ 确认卡核对数量与供应商 → 写入后到 ERP 单据列表核对编号；
3. 看板点「深度诊断」→ 每条结论点开调查步骤，证据数字与步骤观察逐条对得上；
4. 断网/断模型回归：采购卡显示不可用提示；诊断显示降级摘要；日报仍能出规则点。
