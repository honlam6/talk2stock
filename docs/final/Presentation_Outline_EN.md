## Slide 2 — Target users, needs, pain points, scenario (0:10–1:10)

**Purpose:** make the audience recognise the user and the two costs.

**On slide**

- Right: three costs — translation, archive repair, verification.
- Bottom band: Scenario A (complete master data) and B (missing supplier/item); same four tasks, two tools.

**Speaker script**

S1/S2, 16 timed records, n=2 per cell — a pilot, not a significance claim.”

## Slide 3 — Positioning and business value (1:10–2:10)

**Purpose:** define the product boundary and the value claim in one minute.

**On slide**
- Positioning: “A conversational front door to a real ERP.”
- Three verbs: Ask (read-only tools), Draft (editable, validated), Confirm (one human event, one-time token).
- Value panel: 45.0% / 41.8% lower descriptive mean times; 5→0 interruptions; note `n=2 per cell`.
- Boundary: “It does not replace the ERP’s controls, permissions or ledger.”

**Speaker script**
“Talk2Stock is not a replacement ERP. It is the front door: natural language at the ambiguous top of the workflow; the ERP remains the system of record. The model may propose; the human confirms. These pilot numbers are directional, not statistical proof.”

**Avoid:** calling the 45% a proven speed-up.

## Slide 5 — Demo 1: grounded query (2:25–3:15)

**Purpose:** prove that an answer is traceable, not just fluent.

**On slide**
- User: “How much cola is left?”
- Trace: `stock_query(material="cola") → {total: 52, by_depot: …}`.
- Answer: “52 bottles — all in the finished-goods warehouse.”
- Three enforced ideas: tool choice, grounded answer, self-correction.

**Live actions**
1. Type the question.
2. Open “process” trace.
3. Point to 52 in the observation and the answer.

**Speaker script**
“The model chooses the tool, but the number 52 is not generated by the model. It is in the tool observation. If the final contains any number not present there, the review step sends it back to the model. The deterministic template is the last resort.”

## Slide 6 — Demo 2: draft, correction, confirmation (3:15–4:35)

**Purpose:** show the write boundary and conversational correction.

**On slide**
- Four steps: Say it → Validate → Correct → Confirm.
- Correction callout: “30 → 60 bottles · other fields preserved.”
- Actual confirmation card screenshot (60 bottles, ¥210).

**Live actions**
1. Say: “From Meiyijia buy 30 bottles of cola at ¥3.5.”
2. From draft card, say “Change to 60 bottles.”
3. Show that supplier, item, price and warehouse remain; total becomes 210.
4. Open the confirmation card. Do **not** click write unless the audience expects it; explain the token.

**Speaker script**
“The Agent stops at the draft. The refactor keeps the earlier draft in the conversation; a correction changes only the stated field. The confirmation card is not a UI convention: the server issues a one-time HMAC token bound to the draft hash, and editing requires a fresh preview and token. The acceptance write 00000000749 changed stock 0→1 and was rolled back by the controlled seed.”

## Slide 7 — Demo 3: many attachments, one owner each (4:35–5:55)

**Purpose:** show that the unified entry is not text-only.

**On slide**
- Three attachment cards: CSV, TXT, image.
- Agent selects attachment 1 for the purchase and 2 for the sale.
- Two drafts: purchase ¥7.00, sale ¥10.00; each has its own attachment chip.

**Live actions**
1. Select a CSV and a text file in one composer.
2. Type: “The first is the purchase, the second is the sale.”
3. Show two separate draft cards and attachment names.

**Speaker script**
“Each file is parsed locally where possible; the main model only receives a compact catalogue. With multiple files, the tool refuses to guess if the user has not specified ownership. That is deliberate: an agent may plan, but it should not silently merge unrelated records.”

**Fallback:** if upload is slow, use the static attachment diagram and state the actual test result.

## Slide 8 — Technical history: four generations (5:55–6:50)

**Purpose:** show that the final architecture is the result of iteration, not a one-off design.

**On slide**
- Timeline: Transactional prototype (10–19 Oct) → Agent layer + evaluation (24 Oct–9 Nov) → Specialist agents (16 Nov) → Unified boundary (19–22 Nov).
- Bottom strip: 93 commits, two merges, `feature/unified-agent`.
- Metrics per phase: 98.3% historical parse; ask 76.5%→94.1%; specialist suites 4/4, 4/4, 3/3 and debt 15,600=15,600; final 183 tests, 5/5 smoke.

**Speaker script**
“The repository has 93 commits over six weeks and only two merges. Each generation removed a false shortcut: rules became tools, one-shot extraction got validation, free-form writes were replaced by a human token, and many entries became one conversation. The final branch is not merged into main, so this is a proposed final, not a production claim.”

**Answer if asked about branch strategy:** `feature/agent-suite` was pushed but not merged; `feature/unified-agent` is based on it and adds attachments, unified UI, and the final evidence.

## Slide 9 — Technical solution: architecture (6:50–7:45)

**Purpose:** make the separation of responsibilities visible.

**On slide**
- One entry, four planes, one gate diagram.
- Input: text / image / PDF / Word / Excel / current draft.
- Runtime: understand → plan → tool → observe → correct → finish.
- Tools: ERP REST, read-only SQL, parsers, bill check, draft resolver.
- Trust: grounded answer → HMAC token → human confirmation → ERP write + audit.

**Speaker script**
“The Agent can draft, never commit. Reads use the ERP REST business API and a separate read-only SQL channel; writes use the official bill API only after a validated draft and a human confirmation. The ERP source is not modified.”

## Slide 10 — Technical solution: the loop (7:45–8:40)

**Purpose:** answer “is this really an agent?”

**On slide**
- Six-step loop: Understand, Plan & act, Observe, Correct, Answer/draft, Review.
- Budgets: steps + tokens.
- Trace: thought · tool · args · observation.
- Boundary: writes stop at the human gate.

**Speaker script**
“This is not a single model call. Each turn produces one action; the server executes it and feeds back the real observation. Errors, unknown tools, missing fields and ambiguous candidates are normal inputs to the next turn. The answer review can send an ungrounded final back into the loop before the fallback.”

**Possible question:** “Why not native function calling?” Answer: the deployment targets arbitrary OpenAI-compatible endpoints with uneven protocol support; the JSON action loop is portable and auditable.

## Slide 11 — Technical solution: evidence and limits (8:40–9:40)

**Purpose:** put evidence and limits on the same slide, so the claim is defensible.

**On slide**
- Pilot chart: A 88.00→48.45 s; B 86.48→50.29 s; 45.0%/41.8%; 5→0 interruptions.
- Evidence strip: 183/183 tests; 5/5 unified smoke; two files→two drafts; 0 unconfirmed writes.
- Limitations: 2 participants, n=2/cell, order only partially counterbalanced; five smoke cases not a full 71-case rerun; external model endpoint.

**Speaker script**
“These are the numbers we can defend. The pilot is directional; the smoke suite is five core behaviours; the model endpoint is external. The important evidence is the boundary: an acceptance write was performed only after confirmation and then rolled back through seed. We do not claim production scale or statistical significance.”

## Q&A anchors

| Question | Short answer |
|---|---|
| Is the model writing to the database? | No. The draft tool only creates an editable preview; a separate human-confirmed endpoint writes. |
| What prevents replay or tampering? | HMAC token bound to draft hash + persistent nonce blacklist; editing forces a new preview/token. |
| Is 45% real? | It is a descriptive pilot mean, 2 participants, n=2 per cell; not statistically significant. |
| Why not RAG? | Structured numbers require tool observations and grounding; BM25 remains for non-structured retrieval only. |
| What if attachments conflict? | The tool refuses to guess; it returns the catalogue and the Agent asks or retries. |
| What is still missing? | Full unified corpus, production auth/HTTPS, scanned-PDF OCR, legacy Office formats, concurrent load. |
