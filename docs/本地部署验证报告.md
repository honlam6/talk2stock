## 三、本次发现并修复

**1. AI 录入壳僵死（P0）**
- 现象：`:8090` 进程存活、端口 `LISTEN`，但连接后 **0 字节响应**（`curl` → `000` / "Empty reply from server"；raw socket 收 0 字节）。属"能监听却不响应"的僵死态。
- 处理：终止旧进程（PID 36509）→ 重启（新 PID 38313）→ 恢复 HTTP 200。
- 影响面：修复前 AI 录入链路整体不可用（`/api/master`、`/api/parse` 全部无响应）。

**2. `start-all.sh` 加固**
- 缺陷：原第 3 步仅用 `curl -sf` 判活；当 8090 被僵死进程占着端口时，判活失败 → 再起新进程 → **bind 失败被 nohup 静默吞掉** → 服务保持坏的。
- 改法：判活失败 → 先清理占用 8090 的旧进程 → 重启 → 二次确认，失败时明确报错指向日志。

## 七、时区缺陷修复（19:52）——「AI 写了库但 ERP 看不到」

**现象**：AI 录入写入成功（`/api/commit` 返回 200，库里确有单据），但 ERP 单据列表按「今天」筛选看不到。

**根因**：`docker-compose.yml` 只给 `erp-mysql` 设了 `TZ: Asia/Shanghai`，**`erp-backend` 没有 TZ** → JVM 跑 UTC。AI 壳按本地时间写入，被 UTC 的 JVM 解析后落库 +8 小时，单据 `oper_time` 落到次日凌晨（10-11），按「今天(10-10)」自然查不到。

**证据**：
- `docker exec erp-backend date` → UTC；`erp-mysql` / 宿主 → CST
- `jsh_depot_head` 中 3 张单 `oper_time=2026-10-11 03:xx`，而 `create_time=2026-10-10 19:xx`
- 采购入库按「本月」= 2 张，「今天」= 0 张

**修复**：
1. `docker-compose.yml` 给 `erp-backend` 补 `environment: TZ: Asia/Shanghai`，重建容器
2. 修正历史 3 张单：`UPDATE jsh_depot_head SET oper_time = DATE_SUB(oper_time, INTERVAL 8 HOUR) WHERE id IN (277,278,279)`

**验证**：新写单 `00000000676` 的 `oper_time=19:52:47` = 本地时间；采购入库「今天」= 3 张、销售出库「今天」= 1 张；回归 12/12。
